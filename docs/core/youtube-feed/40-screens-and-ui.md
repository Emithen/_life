# 화면 구조와 UI 설계

> 기준: youtube-feed `3f20d6b` · 2026-08-05
> 상태: **설계 문서**. 아직 구현 전이다 — 여기 적힌 것은 "하기로 한 모양"이지 "지금 그런 모양"이 아니다.
> 언제 할지는 `ROADMAP.md` 갈래 1의 2.5단계.

## 왜 이 문서가 생겼나

지금까지 앱은 **한 화면에 전부** 있었다. 채널 추가 폼, 랜덤 추천, 백업·드라이브, 채널 목록이
`index.html` 하나에 세로로 쌓여 있고 `app.js`가 열릴 때 전부 초기화한다.

기능이 다섯을 넘기면서 이게 감당이 안 된다. 그리고 결정적으로 **구독 채널 319개가 들어오면서**
"목록"이라는 것이 처음으로 사람이 훑을 수 없는 크기가 됐다.

---

## 1. 화면 넷과 각자의 책임

| 화면 | 책임 | 여기에만 있는 것 |
|---|---|---|
| **① 채널 관리** | 무엇을 볼지 **고른다** | 구독에서 고르기 · 개별 추가 · 주제 붙이기 · 죽은 채널 정리 |
| **② 메인 피드** | 고른 것의 **최신 영상을 본다** | 채널별 최신 목록, 본 영상 토글, NEW 배지 |
| **③ 랜덤 추천** | 쌓인 풀에서 **하나 고른다** | 재생목록 연동, 무작위 뽑기 |
| **④ 설정** | 데이터를 **관리한다** | 드라이브 동기화, 백업 파일, 풀 비우기, 로그인 |

> ⚠️ 원래 ①은 "채널 추가"였다. **"관리"로 이름이 바뀐 게 이 설계의 핵심 변화다** —
> 추가만 하는 화면이 아니라 **고르고·빼고·정리하는** 화면이다. 이유는 아래 2절.

## 2. ⭐ 구독 ≠ 내 피드

지금 `구독 채널 전부 가져오기`는 구독 목록을 **그대로 `myChannels`에 붓는다**
(`app.js`의 `importSubscriptions`, `topic: "구독"`). 후보도 선별도 없다.
= **"구독한 것은 곧 내가 볼 것"이라는 전제**가 코드에 박혀 있다.

구독이 319개인 사람에게 이 전제는 틀렸다. 구독은 몇 년에 걸쳐 쌓인 것이고,
그중 지금도 보는 건 일부다.

```
구독 목록   = 후보.  구글에서 언제든 다시 받는다 → 저장할 필요조차 없다
myChannels  = 내가 고른 피드.  선별된 것만
```

- `구독 채널 전부 가져오기` 버튼의 동작이 **"전부 추가" → "구독에서 고르기"** 로 바뀐다
- 부수 효과: 백업 파일과 드라이브에 실리는 양이 준다 (319개를 안 싣는다)
- **선별 화면이 곧 마이그레이션이다.** 이미 들어가 있는 319개는 별도 정리 도구 없이
  이 화면에서 "전부 해제 후 고르기" 한 번으로 정리된다

### 선별을 무엇으로 표현하나 — `active` 플래그

| 안 | 대가 |
|---|---|
| 그냥 `myChannels`에서 뺀다 | 제일 싸다. 대신 **손본 `topic`·이름이 사라진다** — 다시 넣으면 `"구독"`으로 리셋 |
| **`{…, active: false}` 로 보관** ✅ | 손본 정보가 남는다. 백업 계약이 "기존 필드 두고 **추가만**"이라 필드 추가는 안전 |

319개에서 40개를 고르는 일은 한 번에 안 끝나고 왔다 갔다 하게 된다.
그때마다 주제를 다시 붙여야 하는 건 못 쓴다 → **플래그 방식.**

⚠️ **`importAll`에 미묘한 영향이 있다.** 채널 병합은 "이미 있으면 스킵"이라
**이 기기의 `active`가 이긴다.** 즉 기기마다 피드 구성이 갈릴 수 있다.
동기화 관점에서 그게 맞는지는 **아직 정하지 않았다** — 붙일 때 판단한다.

## 3. 라우팅 — 해시 라우팅 (React 아님)

`#/feed` · `#/channels` · `#/random` · `#/settings`.

- `app.js`는 이미 `renderMyChannels` / `wirePool` / `wireBackup` / `wireDrive` 로 나뉘어 있다.
  → **"전부 초기화" 를 "보여줄 것 하나만" 으로 바꾸는 수준**이지 재작성이 아니다
- 정적 사이트라 `history.pushState`는 새로고침 시 404가 난다(그 경로에 파일이 없다).
  **해시는 서버 설정 없이 새로고침·뒤로가기가 그냥 된다.**
- 부수 이득: 지금은 열 때 채널·풀·백업·드라이브가 **전부** 초기화된다. 나누면 필요한 것만 뜬다

**왜 React가 아닌가**: `ROADMAP.md` 갈래 1의 3단계 신호등은
"`if`로 화면 조립이 스파게티가 되면"이다. 화면 넷을 나누는 것만으로는 그 지점이 아니다.
프레임워크는 **아플 때** 도입한다 — 지금은 안 아프다.

## 4. 502의 정체 — 부하가 아니라 에러 매핑 (2026-08-05 확인)

콘솔에 `502 Bad Gateway`가 채널마다 뜨는 걸 처음엔 "319개 동시 요청 과부하"로 의심했다.
**직접 쳐보니 아니었다.** 재현되는 결정적 실패고, 셋이 서로 다른 이유였다:

| 채널 | 유튜브 RSS | Worker 응답 | 실제 상황 |
|---|---|---|---|
| `UCo7Kl08…` | **404** | `유튜브 응답 404` | 채널 자체가 없어짐(삭제/정지) |
| `UCQ5rBuSDZ…` | 200 | `영상을 못 찾았어` | 피드는 살아있고 **공개 영상이 0개** |
| `UCPr1OujAE…` | 200 | 같음 | 같음 |

부하라면 새로고침마다 실패하는 채널이 달라졌을 것이다. 같은 채널이 항상 같은 이유로 실패한다.

**진짜 결함은 에러 계약이다.** `worker/rss-proxy.js`가 **모든 예외를 502로 뭉갠다**
(`catch (e) → json({error}, 502)`). 위 셋은 전부 *정상적인 사용자 상황*인데
`502 Bad Gateway`(= 게이트웨이 고장)로 보고된다. `src/worker.js`엔 이미 `err.notFound`
판정이 있는데 502라서 그 길로 가지도 않는다.

→ **고쳐야 할 모양**
- 채널 RSS가 404 → **`notFound`**. 화면은 "없어진 채널"로 표시하고 **정리하라고 안내**한다
- 영상이 0개 → **실패가 아니다.** `200` + `videos: []`. 빈 목록은 정상이다
- 그 밖의 진짜 예외만 502

→ 그래서 **"죽은 채널 정리"가 ① 채널 관리 화면의 기능이 된다.** 319개를 오래 두면 계속 쌓인다.

> ⚠️ 이 확인이 뒤집은 것: **선별(2절)의 근거는 성능이 아니다.**
> 319개 병렬 요청이 실제로 문제인지는 **아직 모른다** — 위 증거로는 알 수 없고 징후도 없다.
> 선별은 "내가 볼 채널만 본다"는 **기획 이유로** 한다. 성능 얘기를 근거로 쓰지 말 것.

## 5. 화면별 내용물

### ① 채널 관리
- **구독에서 고르기** — 구독 목록을 후보로 띄우고 체크. 목록이 300개대라
  **여기에 검색·필터·페이지 분할이 필요하다** (메인 피드가 아니라 이쪽이다)
- **주제 드롭다운** — `topic`은 지금 채널마다 붙는 자유 문자열이고 별도 저장이 없다.
  → **기존 채널들의 `topic`을 모아 목록을 만든다.** 새 저장 구조가 필요 없다.
  새 주제 직접 입력도 되게(콤보박스)
- **유튜브 검색으로 채널 찾기** — ⚠️ 아래 6절의 쿼터 제약을 반드시 지킬 것
- **죽은 채널 정리** — 4절 참고

### ② 메인 피드
선별 후에는 채널이 수십 개 수준이 된다. 주제별로 접거나 나누는 것은 그다음 문제.

### ③ 랜덤 추천
- **내 재생목록 목록에서 고르기** — 지금은 재생목록 ID/URL을 손으로 붙여넣는다.
  `playlists.list?mine=true`(호출당 1 unit)로 목록을 띄운다.
  `youtube.js`의 `pages()`와 `fetchSubscriptions`가 그대로 본이 된다
- ⛔ **WL은 여기에도 안 나온다.** `playlists.list`는 "나중에 볼"·"시청 기록"을 돌려주지 않는다
  → watchme 전용 재생목록 우회는 그대로 유지. **다시 검토하지 말 것**
- ⚠️ `KEYS.playlistId`가 단수라 "여러 재생목록"은 저장 구조 변경 = 별건

### ④ 설정
드라이브 동기화 · 백업 파일 · 풀 비우기 · 로그인/로그아웃. 지금 흩어져 있는 것을 모은다.

## 6. 유튜브 검색의 쿼터 함정 ⚠️

`search.list`는 **호출당 100 units**다. 하루 한도 10,000이면 **하루 100번**.
그리고 재생목록 동기화·구독 가져오기가 **같은 쿼터**를 쓴다
→ 검색으로 소진하면 **그날 앱 전체가 멈춘다.**

**설계 제약 (못박을 것)**
- **자동완성 금지.** 타이핑마다 치면 즉사한다. 명시적 검색 버튼만
- 결과를 캐시한다
- **순서가 앞선 것이 있다: "내 구독에서 찾기"는 0 units다.** 구독이 319개나 있으므로
  검색 수요의 대부분이 여기서 끝난다. 유튜브 검색은 *구독 안 한 채널을 새로 찾을 때*만 필요

## 7. 디자인 시스템

### 컬러 — 화면을 늘리기 **전에** 한다
지금 색이 세 값으로 **22번 하드코딩**돼 있다(`#4a90e2` 9 · `#8a8a8a` 11 · `#c0392b` 2).
CSS 변수로 뽑는 것만으로 8할이 끝난다.

> ⭐ **순서가 중요하다.** 화면이 넷으로 늘어난 뒤에 정리하면 22군데가 80군데가 된다.
> 지금 22군데일 때가 제일 싸다.

`:root { color-scheme: light dark; }`로 다크모드는 이미 자동이다.
변수화하면 다크 전용 값을 따로 줄 여지도 생긴다.

### 컴포넌트와 스타일가이드 — 같은 것의 앞뒤
산출물은 **`styleguide.html` 한 장.** 정적 사이트라 빌드도 라우팅도 필요 없다.

- **컴포넌트 디자인** = 만드는 것(버튼·카드·목록 행·상태줄의 모양을 정한다)
- **프로토타이핑 시스템** = **작업 방식**이다. "덩치 있는 UI는 본 페이지에 넣기 전에
  스타일가이드에서 먼저 본다". 기능이 아니라 규칙이라 **완료 판정이 다르다** — 층위를 갈라 적을 것

### 홈 화면 아이콘 (PWA 최소 조각)
지금 PWA 조각이 **하나도 없다**(manifest·apple 메타·터치 아이콘 전무).
`manifest.json` + 아이콘 몇 장 + 메타 두 줄이면 끝이라 **가장 싸고 완전히 독립적**이다.

⚠️ 다만 앱처럼 띄우는 순간 **오프라인 기대치**가 생긴다. 지금 오프라인에서 되는 건
랜덤 뽑기뿐이다(풀이 localStorage에 있어서). **서비스워커는 별건으로 떼어놓는다.**

## 8. 미정 — "DB 연동"

기기 동기화는 2026-08-04에 **Drive appData**로 정해 구현·검증까지 끝났다(`3f20d6b`).
그래서 "DB를 붙인다"가 무엇을 뜻하는지는 **아직 정하지 않았다.**

> 신호등: **Drive 파일 한 장으로 못 하는 일이 생겼을 때.**
> 예 — 나 아닌 사람과 **공유**해야 한다 / 전체를 **검색·집계**해야 한다 /
> 기기 간에 **즉시** 반영돼야 한다.
> 셋 다 아니면 Drive로 충분하다.

이렇게 적어두면 "언젠가 DB"라는 막연함이 **판정 가능한 조건**이 된다.
