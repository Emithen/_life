# 화면 구조와 UI 설계

> 기준: youtube-feed `02bc62f` · 2026-08-17
> 상태: **2절(구독≠피드·`active`)과 3절(라우팅)은 구현됐다.** 5절의 화면별 내용물은
> 아직 "하기로 한 모양"이다(②의 「더보기」, 주제 드롭다운, 죽은 채널 정리).
> 언제 할지는 `ROADMAP.md` 갈래 1의 2.5단계.

## 왜 이 문서가 생겼나

지금까지 앱은 **한 화면에 전부** 있었다. 채널 추가 폼, 랜덤 추천, 백업·드라이브, 채널 목록이
`index.html` 하나에 세로로 쌓여 있고 `app.js`가 열릴 때 전부 초기화한다.

기능이 다섯을 넘기면서 이게 감당이 안 된다. 그리고 결정적으로 **구독 채널 319개가 들어오면서**
"목록"이라는 것이 처음으로 사람이 훑을 수 없는 크기가 됐다.

## 1. 화면 넷과 각자의 책임

| 화면 | 책임 | 여기에만 있는 것 |
|---|---|---|
| **① 채널 관리** | 무엇을 볼지 **고른다** | 구독에서 고르기 · 개별 추가 · 주제 붙이기 · 죽은 채널 정리 |
| **② 메인 피드** | 고른 것의 **최신 영상을 본다** | 채널별 최신 목록, 본 영상 토글, NEW 배지 |
| **③ 랜덤 추천** | 쌓인 풀에서 **하나 고른다** | 재생목록 연동, 무작위 뽑기 |
| **④ 설정** | 데이터를 **관리한다** | 드라이브 동기화, 로그인 |

> ⚠️ 원래 ①은 "채널 추가"였다. **"관리"로 이름이 바뀐 게 이 설계의 핵심 변화다** —
> 추가만 하는 화면이 아니라 **고르고·빼고·정리하는** 화면이다. 이유는 아래 2절.

## 2. ⭐ 구독 ≠ 내 피드 — ✅ 구현됨 (2026-08-15, `e3931dd`)

> ⭐ **막고 있던 건 선별 UI가 아니라 "훑을 수 있는 목록"이었다.** 채널 관리 화면엔
> 목록 자체가 없었고, 목록은 ② 피드에 영상과 섞여 있었다(채널당 6개). 수백 개를
> 훑는 것이 물리적으로 불가능한 상태 → **영상 없는 한 줄짜리 목록**을 만드는 것이 먼저였다.
> 구현: `isActive`/`setActive`/`setAllActive`(storage) + 목록·☑/☐ 토글·전부 끄기/켜기(app).
> 부수 효과: **꺼진 채널은 Worker 요청조차 안 나간다.**
> ⚠️ **삭제 버튼이 목록에도 필요했다** — 꺼진 채널은 피드에서 사라지므로 피드에만 있던
> 삭제로는 영영 못 지운다. 선별이 만든 구멍이라 같이 막아야 성립한다.

~~지금~~ **2026-08-15 이전까지** `구독 채널 전부 가져오기`는 구독 목록을 **그대로 `myChannels`에 부었다**
(`app.js`의 `importSubscriptions`, `topic: "구독"`). 후보도 선별도 없었다.
= **"구독한 것은 곧 내가 볼 것"이라는 전제**가 코드에 박혀 있었다.
→ 지금은 `active: false`로 담긴다. **후보로 들어오고, 켜야 피드에 나온다.**

구독이 319개인 사람에게 이 전제는 틀렸다. 구독은 몇 년에 걸쳐 쌓인 것이고,
그중 지금도 보는 건 일부다.

```
구독 목록   = 후보.  구글에서 언제든 다시 받는다 → 저장할 필요조차 없다
myChannels  = 내가 고른 피드.  선별된 것만
```

- `구독 채널 전부 가져오기` 버튼의 동작이 **"전부 추가" → "구독에서 고르기"** 로 바뀐다
- 부수 효과: 드라이브에 실리는 양이 준다 (319개를 안 싣는다)
- **선별 화면이 곧 마이그레이션이다.** 이미 들어가 있는 319개는 별도 정리 도구 없이
  이 화면에서 "전부 해제 후 고르기" 한 번으로 정리된다

### 선별을 무엇으로 표현하나 — `active` 플래그

| 안 | 대가 |
|---|---|
| 그냥 `myChannels`에서 뺀다 | 제일 싸다. 대신 **손본 `topic`·이름이 사라진다** — 다시 넣으면 `"구독"`으로 리셋 |
| **`{…, active: false}` 로 보관** ✅ 채택 | 손본 정보가 남는다. 백업 계약이 "기존 필드 두고 **추가만**"이라 필드 추가는 안전 |

⭐ 실제로 붙일 때 **읽는 쪽을 `ch.active !== false`로 썼다.** 그래서 `active`가 아예 없는
기존 채널이 전부 "켜짐"으로 읽히고, **이미 저장된 데이터를 한 줄도 마이그레이션하지 않았다.**
기능을 켜도 첫 화면이 어제와 똑같은 이유이자, 되돌리기가 공짜인 이유(필드를 무시하면 끝).

319개에서 40개를 고르는 일은 한 번에 안 끝나고 왔다 갔다 하게 된다.
그때마다 주제를 다시 붙여야 하는 건 못 쓴다 → **플래그 방식.**

### 선별과 동기화 — 하루 만에 두 번 뒤집힌 곳 (2026-08-15)

`active`를 붙이자마자 "이게 드라이브를 타긴 하나?"가 문제가 됐고, 답을 좇다가
**동기화 규칙 전체가 바뀌었다.** 순서대로 남긴다.

**① 올라가긴 하는데 내려올 때 버려졌다** (`650bc1b`)
`exportAll`은 `active`를 싣고 있었는데 `importAll`이 새 채널을 `topic`·`name`·`channelId`로
**다시 조립**하면서 필드를 버렸다 → 새 기기에서 복원하면 껐던 채널이 전부 켜진 채로 살아났다.
`active === false`일 때만 싣도록 고쳤다("필드 없음 = 켜짐" 규약을 한 갈래로 두려고).

**② 그래도 "이미 있는 채널"엔 전파되지 않았다**
`importAll`이 `have.has()`로 통째로 건너뛰기 때문. 두 기기가 같은 319개를 갖고 있으면
어느 방향으로도 안 맞는다. 원인은 규칙의 성격이었다 — **"기존이 이긴다"는 *쌓이는 것*
(주제·이름·`addedAt`)에 맞게 만들어졌는데, `active`는 쌓이는 게 아니라 선택이다.**

**③ 그래서 합치기를 버렸다 — 대칭 덮어쓰기** (`ee2a4c1`)

| | |
|---|---|
| 올리기 | 내 기기 → 드라이브를 **덮어쓴다** |
| 내려받기 | 드라이브 → 내 기기를 **덮어쓴다** |

내려받기만 교체로 바꿨더니 구멍이 남았다 — 올리기가 여전히 "합친 뒤 올린다"여서
**지운 채널이 클라우드에서 다시 딸려와 되살아났고, 그게 저장돼 클라우드에서도 안 없어졌다.**
합치기는 데이터가 절대 줄지 않아 안전했지만 **바로 그래서 아무것도 지울 수 없었다.**

- ⭐ **안전한 쪽이 늘 옳은 게 아니라, 무엇이 기능인지가 정한다.** 08-05에 합치기를 고른 건
  옳았다 — 그땐 "담아둔 게 사라지지 않는 것"이 목적이었다. 선별이 붙으면서 **"줄이는 것"이
  곧 기능**이 되자, 줄일 수 없는 동기화는 안전한 게 아니라 쓸모없는 게 됐다
- ⭐ **tombstone을 안 만들고 끝났다.** 필드별 시각이라는 정교한 해법을 준비하던 중이었는데,
  규칙을 단순하게 바꾸니 문제가 사라졌다
- ⚠️ 대가: 누르는 쪽이 반대편을 지운다 → 양쪽 다 확인창(몇 개 사라지는지 숫자로)
- ⚠️ 남은 것: 시각 기록이 없어 **마지막에 누른 쪽이 이긴다.** 앱은 최신을 모른다

## 3. 라우팅 — 해시 라우팅 (React 아님) ✅ 구현됨 (2026-08-07)

`#/feed` · `#/channels` · `#/random` · `#/settings`. 예상대로 재작성이 아니라
**끝의 초기화 6줄을 라우터로 바꾸는 수준**으로 끝났다.

- 정적 사이트라 `history.pushState`는 새로고침 시 404가 난다(그 경로에 파일이 없다).
  **해시는 서버 설정 없이 새로고침·뒤로가기가 그냥 된다** — 실제로 `#/random`에서 새로고침·뒤로가기 확인
- 모르는 해시(`#/nope`)와 **해시 없는 주소**는 피드로 떨어진다 → 예전에 공유한 링크가 그대로 열린다

### ⭐ 요소를 지우지 않고 숨긴다 — 이게 이 작업을 싸게 만든 결정

`wire*` 함수가 전부 `getElementById(...)` + `if (!x) return` 가드로 시작한다.
**요소를 DOM에 남겨두면 어느 화면으로 옮기든 그대로 동작한다.** 그래서 이벤트 배선 코드는
한 줄도 안 고쳤고, `showImported()`처럼 **다른 화면의 요소를 건드리는 코드**(`#plInput`)도 무사했다.

> ⚠️ **2026-08-17 React 이식으로 이 결정은 수명을 다했다.** 요소를 남겨두는 것은
> "getElementById로 잡기 때문에" 필요했던 것인데, React는 상태에서 화면을 만들므로
> **안 보는 화면은 아예 안 그린다.** `showImported()`처럼 다른 화면을 건드리던 코드도
> 사라졌다 — 상태를 App에 모아두면 "화면을 찾아가 고치는" 일 자체가 없다.
> ⭐ 결정이 틀렸던 게 아니다. **그때의 제약(빌드 없음·DOM 직접 조작) 아래서는 옳았고,
> 제약이 바뀌자 필요가 없어졌다.** 이런 항목은 지우지 말고 이렇게 표시해 남긴다.

### 부수 이득이 실은 본전이었다 — 피드 렌더만 지연시킨다

나머지 `wire*`는 이벤트만 붙이므로 싸다. **비싼 초기화는 `renderMyChannels()` 하나뿐**이고
이건 **채널 수만큼 Worker 요청**을 낸다. 그래서 이것만 피드 화면에 처음 들어올 때 부른다.

- 채널 2개를 넣고 `#/settings`로 열어 **요청 0회 · `#my`가 비어 있는 것**을 확인
- ⚠️ **재진입 때 다시 그리면 안 된다.** 탭을 오갈 때마다 요청이 다시 나가면 예전보다 나빠진다
  → `feedRendered` 플래그를 **`renderMyChannels()` 안에서** 세운다
  → **2026-08-17부터는 `epoch`다.** 깃발을 손으로 내리는 대신 "채널이 바뀌면 숫자가 오른다"로
    바꿨다. `feedRendered = false`를 빠뜨리는 실수가 구조적으로 불가능해진다.
    ⚠️ 이식 중에 이 자리에서 버그를 둘 냈다(둘 다 React 특유의 함정이라 옛 코드엔 없던 것):
    ① 받아온 결과를 **화면 컴포넌트가 들고 있으면** 탭을 옮길 때 통째로 사라져 아끼는 의미가 없다
       → 결과도 `App`에 둔다
    ② "이미 받아왔다" 표시를 **state로 두면 요청이 정확히 두 배**가 된다(StrictMode가 이펙트를
       두 번 도는데 첫 실행의 setState가 아직 반영 안 됨) → **ref로 동기 처리**
    실측: 탭 6회 왕복 → 요청 0건 / 채널 토글 후 복귀 → 채널 수와 정확히 같은 수
- ⚠️ **2026-08-15 정정**: 원래는 채널 추가·구독 가져오기·복원이 **곧바로 `renderMyChannels()`를
  불렀다**("그때 이미 최신이 그려지니까"). 그런데 그 셋은 전부 **다른 화면에서** 일어난다 —
  보이지도 않는 피드를 그리느라 채널 수만큼 요청이 나갔다. 지금은 **깃발만 내리고**
  실제로 그리는 건 피드로 갈 때다

### 로그인 버튼과 구독 버튼이 서로 다른 화면에 갈렸다

`wireAuth`가 유일하게 화면 둘에 걸치는 함수다 — 로그인 버튼은 ④ 설정, `구독 가져오기`는 ① 채널 관리.
로그아웃 상태에서 구독 버튼이 그냥 사라지면 이유를 알 수 없어서, 대신 **설정으로 가라는 안내**(`#subsHint`)를
띄우고 로그인하면 감춘다. 함수를 쪼개는 대신 안내 한 줄로 메웠다.

**왜 React가 아닌가** (2026-08-07 판단): `ROADMAP.md` 갈래 1의 3단계 신호등은
"`if`로 화면 조립이 스파게티가 되면"이다. 화면 넷을 나누는 것만으로는 그 지점이 아니다.
프레임워크는 **아플 때** 도입한다 — 지금은 안 아프다.
(실제로 라우터는 `SCREENS` 배열 하나 + `hidden` 토글이 전부다. 스파게티와는 거리가 멀다.)

> ✅ **2026-08-17에 React로 갔다. 다만 신호등이 바뀐 게 아니라 근거가 달랐다.**
> 화면 조립이 스파게티가 돼서가 아니라, **다음 두 작업(유튜브 검색 UI·구독/추가 분리)이
> 전부 채널 화면에 얹히기 때문**이다. 바닐라로 먼저 만들면 그 코드가 이식 때 같이 버려진다.
> ⭐ **"아플 때 도입"은 지켜졌다** — 아픈 곳이 "지금 화면"이 아니라 **"곧 할 작업"**이었을 뿐이다.
> 실제로 버린 건 화면 조립 780줄뿐이고 `lib/` 넷은 로직 그대로 건너왔다.

## 4. 502의 정체 — 부하가 아니라 에러 매핑 (2026-08-05 확인)

콘솔에 `502 Bad Gateway`가 채널마다 뜨는 걸 처음엔 "319개 동시 요청 과부하"로 의심했다.
**직접 쳐보니 아니었다.** 재현되는 결정적 실패고, 셋이 서로 다른 이유였다:

| 채널 | 유튜브 RSS | Worker 응답 | 실제 상황 |
|---|---|---|---|
| `UCo7Kl08…` | **404** | `유튜브 응답 404` | 채널 자체가 없어짐(삭제/정지) |
| `UCQ5rBuSDZ…` | 200 | `영상을 못 찾았어` | 피드는 살아있고 **공개 영상이 0개** |
| `UCPr1OujAE…` | 200 | 같음 | 같음 |

부하라면 새로고침마다 실패하는 채널이 달라졌을 것이다. 같은 채널이 항상 같은 이유로 실패한다.

**진짜 결함은 에러 계약이다.** `worker/rss-proxy.js`가 **모든 예외를 502로 뭉갠다**
(`catch (e) → json({error}, 502)`). 위 셋은 전부 *정상적인 사용자 상황*인데
`502 Bad Gateway`(= 게이트웨이 고장)로 보고된다. `src/lib/worker.ts`엔 이미 `err.notFound`
판정이 있는데 502라서 그 길로 가지도 않는다.

→ **고쳐야 할 모양**
- 채널 RSS가 404 → **`notFound`**. 화면은 "없어진 채널"로 표시하고 **정리하라고 안내**한다
- 영상이 0개 → **실패가 아니다.** `200` + `videos: []`. 빈 목록은 정상이다
- 그 밖의 진짜 예외만 502

→ 그래서 **"죽은 채널 정리"가 ① 채널 관리 화면의 기능이 된다.** 319개를 오래 두면 계속 쌓인다.

> ⚠️ 이 확인이 뒤집은 것: **선별(2절)의 근거는 성능이 아니다.**
> 319개 병렬 요청이 실제로 문제인지는 **아직 모른다** — 위 증거로는 알 수 없고 징후도 없다.
> 선별은 "내가 볼 채널만 본다"는 **기획 이유로** 한다. 성능 얘기를 근거로 쓰지 말 것.

### ② 메인 피드
선별 후에는 채널이 수십 개 수준이 된다. 주제별로 접거나 나누는 것은 그다음 문제.

**채널당 3개만 보이고 「더보기」로 6개까지 (2026-08-05 추가, 착수 전)**
채널이 수십 개면 채널당 6개는 스크롤이 너무 길다. 기본을 3개로 접고 펼치게 한다.

⚠️ **이건 2026-07-30의 결정을 되돌리는 것이다.** 그때 3 → 6으로 늘렸고, 이유가 코드에 남아 있다:

```js
export const LIMIT = 6; // 채널당 보여줄 최신 영상 수 (본 영상이 흐려지므로 3개는 너무 적었다)
```

**본 영상이 흐려지기 때문에** 3개면 실질적으로 볼 게 없었다는 것이다.
그냥 3으로 되돌리면 **그때 그 문제가 그대로 재발한다** — 맨 위 3개가 전부 본 영상이면
접힌 상태에서 보이는 새 영상이 **0개**가 된다.

→ **그래서 "앞에서 3개"가 아니라 「안 본 영상 3개」로 세는 안을 같이 검토한다.**
본 영상은 접기 대상으로 먼저 밀어 넣으면 07-30의 문제가 사라진다.
(단순히 앞 3개 / 안 본 것 3개 — **아직 안 정했다.** 붙일 때 판단한다.)

**⭐ `LIMIT`은 건드리지 않는다. 바꾸는 건 화면의 표시 개수뿐이다.**
- `src/lib/worker.ts`의 `LIMIT = 6`은 **Worker 요청 파라미터**(`/rss?…&limit=6`)다
- Worker는 RSS 응답(최근 ~15개)을 받아 **잘라서** 준다(`rss-proxy.js`의 `slice`)
  → `limit`을 줄여도 **유튜브 쪽 비용은 그대로**다. 아낄 게 없다
- 6개를 계속 받아두면 **「더보기」가 네트워크 0회**로 즉시 펼쳐지고, `channelCache`에도 6개가 남는다
- 3개만 받아오게 바꾸면 더보기마다 요청이 생긴다 — **이득 없이 손해만 있는 방향**이니 하지 말 것
- 참고: Worker 상한이 15라(`Math.min(limit, 15)`) 나중에 6 → 10~15로 넓히는 것도 추가 비용이 없다

**남은 결정**: 「더보기」 상태를 기억할 것인가. 채널별 개별 토글은 자연스럽지만,
저장하면 `myChannels`에 필드가 하나 더 붙는다(백업 계약 영향). **세션 한정(저장 안 함)을 권한다.**

### CSS 관리 전략 (2026-08-05 결정)

스타일은 **`src/style.css` 한 장**이었다(같은 날 `index.html`의 `<style>`에서 분리).

> ⚠️ **2026-08-17에 Tailwind로 갔다.** 아래 ①②③의 **판단은 그대로 살아 있고**, 표현만
> 바뀌었다 — 색 토큰 7개는 `@theme`으로 옮겼고(토큰이 곧 클래스 이름이 되어 색을 직접
> 쓸 길이 막힌다), `@layer`가 하던 특정도 정리는 Tailwind가 대신한다.
> ⚠️ 다만 **Tailwind의 preflight는 전면 리셋이라 ①의 방침과 정면으로 충돌한다** —
> `h1`·`p`의 여백을 지운다. 그래서 base에서 되돌렸다. 아래 ①을 읽을 땐 이 점을 같이 본다.

셋으로 정리:

**① reset — 전면 도입 안 함. 최소 3줄만.**
전면 리셋(Meyer reset 류)은 안 한다. 지금 화면은 브라우저 기본값 위에 얹혀 있고
(`h1`·`p` 여백, `color-scheme: light dark`가 주는 다크모드 기본색),
전면 리셋은 그걸 지운 만큼 다시 쓰게 만든다. **실제로 아팠던 것만** 골랐다:

| 줄 | 고친 실제 문제 |
|---|---|
| `box-sizing: border-box` | 입력칸·버튼·textarea가 컨테이너보다 **22~32px 튀어나오고 있었다** |
| `img, svg { max-width: 100% }` | 썸네일 붙일 때 대비 |
| `button,input,… { font-family: inherit }` | `#chInput`은 **Arial**, `.pool input`은 -apple-system으로 **갈려 있었다** |

세 번째 줄이 값을 한 이유: 개별 규칙마다 `font-family: inherit`을 반복해 적던 게
**그 규칙이 없어서 생긴 증상**이었다. 한 줄로 걷어냈다.

**② 다중 파일 대신 `@layer`**
파일을 쪼개면 빌드 단계가 없어서 `@import`(순차 로딩이라 느리다)를 쓰거나
`<link>`를 여러 개 걸어야 하는데, 후자는 **`?v=`를 파일 수만큼 손으로** 관리해야 한다.
이미 여섯 곳이다 → 늘릴 이유가 없다.

```css
@layer reset, tokens, base, components, screens;
```

진짜 이득은 정리정돈이 아니라 **특정도 싸움의 예방**이다. 화면별 규칙이 컴포넌트를
덮을 때 `!important`나 셀렉터 중첩으로 이길 필요가 없다 — `screens`가 뒤라서 그냥 이긴다.
**화면 분리(2.5단계)를 대비해 `screens` 레이어를 미리 비워뒀다.**

> ✅ **2026-08-07에 값을 했다.** 탭 링크(`.tabs a`)가 `base`의 `a`(파랑·1.05rem·600)를
> **셀렉터 한 개로** 덮어 회색 보조 링크가 됐다. 레이어가 없었으면 `nav.tabs a`처럼
> 특정도를 올리거나 `!important`를 썼을 자리다. 지금 `screens`에 든 것은
> `.screen[hidden]` · `.screen > :first-child` · `.tabs` 넷뿐이다.
→ 개념 정리: `_life/concepts.md`의 「CSS @layer」

⚠️ **레이어 밖 규칙은 모든 레이어보다 강하다.** 직관과 반대다(실제로 확인함).
새 규칙을 추가할 때 **반드시 어느 레이어 안에** 넣을 것. 밖에 두면 그게 전부를 이긴다.

**③ 프레임워크는 지금 대비하지 않는다**
Tailwind는 이 프로젝트에 맞지 않는다 — 빌드 단계를 강제해 "아프기 전엔 도입 안 한다"에
정면으로 반하고, CSS를 배우는 중인데 배우는 대상이 클래스 이름 외우기로 바뀐다.

React로 갈 때(갈래1 3단계) 무엇이 살아남는가:

| 지금 자산 | React로 갈 때 |
|---|---|
| `:root` 색 토큰 | ✅ **그대로 산다.** 프레임워크 무관한 CSS 표준 |
| `@layer` 구조 · `base` 레이어 | ✅ 대체로 산다 |
| `.controls`·`.pool` 컴포넌트 규칙 | ❌ 컴포넌트로 다시 쓰게 된다 |

→ **토큰을 뽑아둔 것이 이미 최선의 프레임워크 대비다.** 그 이상 미리 할 건 없다.
컴포넌트 CSS는 어차피 다시 쓰이므로 "나중에 React에서도 쓰게" 설계하려는 노력은 낭비다.

> 🚦 **신호등: `?v=`를 손으로 맞출 곳이 여섯을 넘으면 빌드 단계를 들일 때다.**
> 그 시점은 대체로 React(갈래1 3단계) 시점과 같다 — **둘을 따로 결정하지 말 것.**

### 컴포넌트와 스타일가이드 — 같은 것의 앞뒤
산출물은 **`styleguide.html` 한 장.** 정적 사이트라 빌드도 라우팅도 필요 없다.

> **CSS 파일을 쪼갤 때가 딱 한 번 있다면 여기다.** `styleguide.css`는 배포되는 화면이
> 아니므로 본 앱 CSS를 오염시키지 않게 따로 둔다. 위 ②의 "쪼개지 마라"는 **앱 CSS** 얘기다.

- **컴포넌트 디자인** = 만드는 것(버튼·카드·목록 행·상태줄의 모양을 정한다)
- **프로토타이핑 시스템** = **작업 방식**이다. "덩치 있는 UI는 본 페이지에 넣기 전에
  스타일가이드에서 먼저 본다". 기능이 아니라 규칙이라 **완료 판정이 다르다** — 층위를 갈라 적을 것

### 홈 화면 아이콘 (PWA 최소 조각) — ✅ 완료 (2026-08-05)
`manifest.json` + `icons/` + `<head>` 메타 몇 줄. 예상대로 가장 싸고 완전히 독립적이었다.

**⚠️ 안드로이드와 iOS가 서로 다른 걸 본다** — 이게 이 작업의 유일한 함정이다.
- 안드로이드 → `manifest.json`의 `icons`
- iOS → **manifest를 무시하고 `apple-touch-icon` 하나만** 본다 → 따로 걸어야 한다

**그래서 원본 SVG가 둘이다.** 같은 도형인데 용도가 다르다:

| 원본 | 만드는 것 | 왜 따로인가 |
|---|---|---|
| `icons/icon.svg` (모서리 둥글, 투명) | `icon-192/512.png` (`purpose: any`) | 앱 목록·탭에 그대로 놓이는 자리 |
| `icons/icon-square.svg` (꽉 찬 불투명) | `icon-maskable-512.png`, `apple-touch-icon.png` | **OS가 자기 모양으로 깎는 자리.** 투명이 있으면 귀퉁이가 검게 뜬다 |

- `icon-square.svg`의 삼각형이 더 작은 건 실수가 아니라 **maskable 안전 영역**(가운데 지름 80% 원) 때문이다
- `apple-touch-icon.png`는 **반드시 불투명**이어야 한다 (`sips -g hasAlpha`로 확인 가능)
- PNG 재생성 명령은 각 SVG 주석에 적어뒀다(`rsvg-convert`, `og-image.svg`와 같은 방식)

**서비스워커는 일부러 안 넣었다.** 없어도 "홈 화면에 추가"와 아이콘은 정상 동작한다
(크롬의 자동 설치 배너만 안 뜬다). 앱처럼 띄우는 순간 **오프라인 기대치**가 생기는데,
지금 오프라인에서 되는 건 랜덤 뽑기뿐이라(풀이 localStorage에 있어서)
**만들 수 없는 기대를 먼저 만들지 않는다.** 오프라인 지원은 별건.

⚠️ `background_color`는 `#0f1115`(어두움)로 뒀다. 실행 시 스플래시 색인데,
앱은 `color-scheme: light dark`라 **라이트 모드에서는 잠깐 어두웠다가 밝아진다.**
manifest는 미디어 쿼리를 못 받아 한 값만 가능하다 — 거슬리면 흰색으로 바꾼다.

## 8. 미정 — "DB 연동"

기기 동기화는 2026-08-04에 **Drive appData**로 정해 구현·검증까지 끝났다(`3f20d6b`).
그래서 "DB를 붙인다"가 무엇을 뜻하는지는 **아직 정하지 않았다.**

> 신호등: **Drive 파일 한 장으로 못 하는 일이 생겼을 때.**
> 예 — 나 아닌 사람과 **공유**해야 한다 / 전체를 **검색·집계**해야 한다 /
> 기기 간에 **즉시** 반영돼야 한다.
> 셋 다 아니면 Drive로 충분하다.

이렇게 적어두면 "언젠가 DB"라는 막연함이 **판정 가능한 조건**이 된다.
