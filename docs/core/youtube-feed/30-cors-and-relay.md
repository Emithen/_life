# CORS·릴레이·캐싱

> 기준: youtube-feed `3b7f8cb` · 2026-07-30

## 1. CORS — 왜 릴레이가 필요한가

브라우저 보안 규칙:
> **"내가 있는 사이트(emithen.github.io)가 아닌 다른 도메인(youtube.com)의 데이터를,
> 상대가 허락하지 않으면 자바스크립트로 읽을 수 없다."**

유튜브 RSS는 "다른 사이트에서 읽어도 된다"는 허락 헤더(`Access-Control-Allow-Origin`)를 주지 않는다.
→ 브라우저에서 직접 `fetch`하면 차단된다.

**릴레이(프록시)가 뚫는 원리**: 프록시는 브라우저가 아니라 그냥 서버라서 이 규칙에 안 걸린다.
유튜브에서 받아온 뒤, 브라우저에게 넘길 때 "읽어도 된다" 허락 헤더를 붙여준다.

> 참고: `collect.py`(GitHub Actions)는 이 문제가 아예 없다. 서버끼리 통신이라 CORS는 브라우저만의 규칙.

## 2. 릴레이의 진화

| 단계 | 방식 | 문제 |
|---|---|---|
| 1차 | 공개 무료 프록시 1개 (allorigins) | 개발 중 500 에러로 즉시 다운 확인 |
| 2차 | 공개 프록시 3개 **순차 폴백** | 레이트 리밋·과부하 시 **3개가 동시에 막혀** "3연속 실패" |
| **3차 (현재)** | **내 Cloudflare Worker** | 공개 프록시 전부 제거. 폴백 없음(단일 의존) |

### 왜 3개를 둬도 3연속 실패하나

셋 다 모르는 사람이 자선/취미로 띄운 무료 공용 서버다. 실패가 **독립적이지 않다**:
- 채널 여러 개 = 새로고침마다 동시 요청 폭증 → **레이트 리밋**에 한꺼번에 걸림
- @핸들이면 1MB 페이지 긁기 + RSS = 요청 2배
- 12초 타임아웃 — 다들 느린 순간이면 셋 다 초과

즉 폴백은 "하나가 죽는" 상황엔 통하지만, **"같은 이유로 다 막히는"** 상황엔 안 통한다.

### 3차 — 내 Worker (L3 내재화, 2026-07-28 배포)

```
GET https://yt-rss.javer1155.workers.dev/rss?ch=@핸들&limit=3
→ { channelId, name, videos: [...] }   ← data.json sections와 같은 모양
```

- 남의 서버 안 씀 → 레이트 리밋·다운 리스크 소멸 (나만 씀)
- @핸들 해결을 서버가 하니 **~20초 → ~1초** (실측 0.5~2초)
- XML 파싱·채널명 추출까지 Worker가 담당 → 프론트는 계약(JSON) 하나만 다루면 됨
- `ALLOWED_ORIGINS`로 내 사이트에서만 쓰게 제한 (남이 내 Worker를 공짜 프록시로 못 쓰게)
- 무료 한도 하루 10만 요청 — 이 규모엔 한참 남음
- **트레이드오프**: 폴백을 없앴으므로 Worker가 죽으면 내 채널 기능도 멈춘다.
  대신 원인이 한 곳뿐이라 진단이 쉽고, 무료 공용 프록시보다 훨씬 안정적이다.
- 코드 고치는 법: `worker/README.md` (대시보드에 붙여넣고 Deploy. 전파에 ~20초)

## 3. 파싱 방식이 세 군데서 다른 이유 ⭐

같은 XML을 읽는데 코드 모양이 다르다. **환경이 제공하는 도구가 다르기 때문.**

| 위치 | 방식 | 왜 |
|---|---|---|
| `collect.py` (Actions) | `xml.etree.ElementTree` | 파이썬 표준 XML 파서 |
| `worker/rss-proxy.js` | **정규식 + indexOf** | **Workers엔 DOMParser가 없다** (브라우저가 아님) |
| `app.js` (브라우저) | **파싱 안 함** | Worker가 JSON으로 주므로 그릴 뿐 (예전엔 `DOMParser`를 썼다) |

## 4. XML 엔티티 디코딩

XML에선 `<`, `&`를 그대로 못 써서 `&lt;`, `&amp;`로 저장한다.
제목에 `&`가 든 영상은 RSS에 `&amp;`로 들어있어, 되돌리지 않으면 화면에 `&amp;`가 그대로 보인다.
→ `decode()`가 처리. **`&amp;`를 마지막에 푸는 순서가 중요** (먼저 풀면 `&amp;lt;`가 꼬임).

## 5. 캐싱 — 두 종류

| 종류 | 위치 | 효과 |
|---|---|---|
| **엣지 캐시** | Worker가 유튜브를 부를 때 (`cf.cacheTtl`) | 영상 10분 / 핸들→ID 1시간. 유튜브 부담·속도 개선 |
| **HTTP 캐시** | Worker 응답 (`max-age=600`) | 브라우저가 10분 보관. ⚠️ 수정 직후엔 옛 응답이 보일 수 있음 |
| **localStorage 캐시** | 브라우저 | 재방문 시 **이전 결과를 즉시 그리고**, 뒤에서 조용히 갱신해 교체 → 체감 속도 급상승 |

### 캐시 관련 필수 규칙 (실제로 데여서 얻음)

- **`Vary: Origin`** — 응답의 CORS 헤더가 Origin마다 다르므로 캐시도 Origin별로 갈라야 한다.
  없으면 localhost용 응답이 github.io 요청에 재사용돼 `Failed to fetch`.
- **에러는 `Cache-Control: no-store`** — 일시적 장애가 10분간 굳는 걸 방지.
- 자세한 사고 기록: `90-gotchas.md` 10·11번

## 6. 실패를 다루는 태도

- `collect.py`: 채널마다 `try/except` → 9개 중 1개 실패해도 나머지 8개는 나온다.
- `app.js`: 채널별로 따로 fetch → 하나 실패해도 그 칸만 "불러오기 실패"로 표시.
- **원칙**: 남의 서비스는 반드시 가끔 실패한다고 가정하고, 부분 실패를 격리한다.

## 7. XSS 방지

영상 제목을 화면에 넣을 때 `innerHTML`이 아니라 **`textContent`**를 쓴다.
제목에 `<script>`가 들어있어도 글자로만 취급돼 실행되지 않는다.
→ 남이 만든 데이터를 화면에 넣을 땐 항상 이렇게.
