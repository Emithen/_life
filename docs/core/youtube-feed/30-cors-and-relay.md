# CORS·릴레이·캐싱

> 기준: youtube-feed `c54eaef` · 2026-08-29

## 1. CORS — 왜 릴레이가 필요한가

브라우저 보안 규칙:
> **"내가 있는 사이트(emithen.github.io)가 아닌 다른 도메인(youtube.com)의 데이터를,
> 상대가 허락하지 않으면 자바스크립트로 읽을 수 없다."**

유튜브 RSS는 "다른 사이트에서 읽어도 된다"는 허락 헤더(`Access-Control-Allow-Origin`)를 주지 않는다.
→ 브라우저에서 직접 `fetch`하면 차단된다.

**릴레이(프록시)가 뚫는 원리**: 프록시는 브라우저가 아니라 그냥 서버라서 이 규칙에 안 걸린다.
유튜브에서 받아온 뒤, 브라우저에게 넘길 때 "읽어도 된다" 허락 헤더를 붙여준다.

> 참고: 옛 `collect.py`(GitHub Actions)엔 이 문제가 아예 없었다. 서버끼리 통신이라 CORS는 브라우저만의 규칙.
> **"브라우저로 옮기니 CORS가 생겼다"** — 릴레이가 필요해진 건 이 이동의 대가다.

## 2. 릴레이의 진화

| 단계 | 방식 | 문제 |
|---|---|---|
| 1차 | 공개 무료 프록시 1개 (allorigins) | 개발 중 500 에러로 즉시 다운 확인 |
| 2차 | 공개 프록시 3개 **순차 폴백** | 레이트 리밋·과부하 시 **3개가 동시에 막혀** "3연속 실패" |
| **3차 (현재)** | **내 Cloudflare Worker** | 공개 프록시 전부 제거. 폴백 없음(단일 의존) |

### 왜 3개를 둬도 3연속 실패하나

셋 다 모르는 사람이 자선/취미로 띄운 무료 공용 서버다. 실패가 **독립적이지 않다**:
- 채널 여러 개 = 새로고침마다 동시 요청 폭증 → **레이트 리밋**에 한꺼번에 걸림
- @핸들이면 1MB 페이지 긁기 + RSS = 요청 2배
- 12초 타임아웃 — 다들 느린 순간이면 셋 다 초과

즉 폴백은 "하나가 죽는" 상황엔 통하지만, **"같은 이유로 다 막히는"** 상황엔 안 통한다.

### 3차 — 내 Worker (L3 내재화, 2026-07-28 배포)

```
GET https://yt-rss.javer1155.workers.dev/rss?ch=@핸들&limit=3
→ { channelId, name, videos: [...] }   ← data.json sections와 같은 모양
```

- 남의 서버 안 씀 → 레이트 리밋·다운 리스크 소멸 (나만 씀)
- @핸들 해결을 서버가 하니 **~20초 → ~1초** (실측 0.5~2초)
- XML 파싱·채널명 추출까지 Worker가 담당 → 프론트는 계약(JSON) 하나만 다루면 됨
- `ALLOWED_ORIGINS`로 내 사이트에서만 쓰게 제한 (남이 내 Worker를 공짜 프록시로 못 쓰게)
  - ⚠️ **배포 주소를 옮기면 여기를 고치고 Worker를 재배포해야 한다.** 안 하면 CORS로
    채널이 **하나도** 안 뜬다.
  - ✅ **옛 주소(`emithen.github.io`)는 2026-08-25에 뺐다.** 이사가 끝날 때까지만 남겨뒀던 것이고
    (2026-08-17에 끝났다), 그 뒤로는 **낡은 데이터가 드라이브를 덮을 경로**로만 남아 있었다
  - ⚠️ Vercel **프리뷰 주소는 배포마다 바뀌어** 등록이 불가능하다 → 프리뷰에선 안 되는 게 정상
- 무료 한도 하루 10만 요청 — 이 규모엔 한참 남음
- **트레이드오프**: 폴백을 없앴으므로 Worker가 죽으면 내 채널 기능도 멈춘다.
  대신 원인이 한 곳뿐이라 진단이 쉽고, 무료 공용 프록시보다 훨씬 안정적이다.
- 코드 고치는 법: `worker/README.md` (대시보드에 붙여넣고 Deploy. 전파에 ~20초)

### Worker는 이제 한 갈래뿐이다 (2026-07-31 일원화 이후)

| 경로 | 뒤에서 무엇을 부르나 | 인증 | 쓰는 곳 |
|---|---|---|---|
| `/rss?ch=` | 유튜브 **RSS**(공개) + 채널 페이지 HTML | 없음 | 내 채널 목록 |

`/` 로 열면 살아있는지와 사용법을 돌려준다(헬스체크).
→ **`usage`에 `/rss` 하나만 나오면 지금 코드**다. `/playlist`·`/videos`가 보이면 옛 버전이 올라간 것.

`/playlist`·`/videos`(YouTube Data API)는 걷어냈다. 구글 로그인이 붙으면서 브라우저가 유튜브를
직접 부르기 때문이다(`src/lib/youtube.ts`). **이 Worker는 더 이상 API 키를 쓰지 않는다** —
Cloudflare의 `YT_API_KEY` 시크릿도 지웠다.

### 왜 한때 Data API를 Worker에 뒀었나 (기록)

- **재생목록 RSS는 최근 15개만** 준다. 랜덤 추천은 폭이 넓어야 의미가 있어서 부족했다.
- 유튜브 "나중에 볼"(WL)은 **2016-09-12부터 API로도 빈 목록**, RSS는 404. 아예 길이 없다.
  → 사용자가 만든 **전용 재생목록**(`watchme`)을 대신 읽는다.
- 그래서 **키 관리**가 생겼었다. 브라우저에서 Data API를 직접 부르면 키가 노출되니
  Worker가 "비밀을 감추는 역할"까지 맡았다.
- **로그인이 이 문제를 통째로 없앴다.** 토큰은 사용자 본인 것이라 감출 이유가 없고,
  덤으로 비공개 재생목록까지 읽힌다(API 키로는 '일부 공개'까지가 한계였다).
  → 릴레이의 존재 이유가 둘에서 **CORS 하나로** 줄었다.

### OAuth 호출은 왜 Worker를 안 거치나 ⭐ (2026-07-31 로그인 추가)

릴레이를 둔 이유가 ① CORS 우회 ② API 키 숨기기 두 가지였는데, **OAuth 호출은 둘 다 해당이 없다.**

| | 유튜브 RSS | 유튜브 Data API (OAuth) |
|---|---|---|
| CORS | ❌ 허락 안 함 → 릴레이 필요 | ✅ `googleapis.com`이 허용 |
| 자격 | 공용 API 키(내 것, 숨겨야 함) | 사용자 본인 토큰(숨길 이유 없음) |

그래서 로그인 뒤의 호출은 **브라우저가 유튜브를 직접** 부른다. 오히려 그게 안전하다 —
사용자 토큰을 내 서버로 보내지 않기 때문이다.

> ⚠️ **이 문장은 2026-08-25부터 절반만 사실이다** (✅ 구현됨 — `04ab226`).
> 인증이 Authorization Code flow(코드 모델)로 가면서 **서버가 code를 교환**하므로 액세스
> 토큰이 한 번 내 서버를 거친다. 다만 **경유일 뿐 보관은 안 한다** — 서버는 `sub`만 꺼내고,
> 액세스 토큰은 브라우저로 넘기고, refresh 토큰은 버린다. **유튜브 호출은 계속 브라우저가
> 직접 한다.** ⭐ 그 결과 **서버에 남는 비밀은 `client_secret` 하나뿐**이다.
> → 계약과 근거는 `10-flow-and-contracts.md` 2-c절

### 한도를 코드로 못 박아둔 곳 (지금은 `src/lib/youtube.ts`에 있다)

- `MAX_PAGES = 20` — 50개 × 20페이지 = **최대 1000개**. 재생목록이 아무리 길어도 여기서 멈춘다.
- `CHUNK = 50` — `videos.list`가 한 번에 받는 최대.
- Data API 비용: 호출 1회 = **1 unit**. 하루 10,000 unit인데 이제 **내 계정 쿼터**에서 나간다
  (예전엔 Worker의 공용 키에서 나갔다). 규모상 여유롭다.

### 왜 채널 피드는 RSS로 남겨뒀나 ⭐

로그인이 붙었으니 채널 최신 영상도 Data API로 받을 수 있다
(`UC...` 채널의 업로드 재생목록은 `UU...`, 앞 두 글자만 바꾸면 된다). 그런데 안 바꿨다:

| | RSS (지금) | Data API로 바꾼다면 |
|---|---|---|
| 쿼터 | **0** | 채널 수만큼 (채널 50개 = 새로고침 1회당 50 unit) |
| 로그인 | 불필요 | 필수 — 로그아웃 상태면 첫 화면이 통째로 빈다 |

**앱을 여는 것 자체에 값이 붙는 구조**가 되므로 "무료·무관리" 원칙에 어긋난다.
→ 자주 부르는 것은 RSS(공짜), 어쩌다 부르는 것은 Data API. 이 경계가 지금 구조의 기준이다.

> 다만 Worker에서 제일 약한 조각인 **`@핸들 → channel_id` 긁기**는 옮길 만하다.
> `channels.list?forHandle=@mkbhd`(1 unit)로 대체 가능하고, 채널 추가는 어쩌다 하는 일이라
> 쿼터가 사실상 안 나간다. 이 긁기는 `90-gotchas.md` 4·8·9번에서 **세 번** 사고를 냈다. (미착수)

같은 XML을 읽는데 코드 모양이 다르다. **환경이 제공하는 도구가 다르기 때문.**

| 위치 | 방식 | 왜 |

| `src/lib/worker.ts` (브라우저) | **파싱 안 함** | Worker가 JSON으로 주므로 받아 넘길 뿐 (예전엔 `app.js`가 `DOMParser`를 썼다) |
| `src/lib/youtube.ts` (브라우저) | **파싱 안 함** | Data API가 JSON으로 준다. 우리 계약 모양으로 옮겨 담기만 한다 |
| `src/screens/*.tsx` (브라우저) | **네트워크를 아예 모름** | `lib/worker.ts`가 준 JSON만 그린다 (2026-07-31 분리, 08-17 React 이식에도 그대로) |

## 4. XML 엔티티 디코딩

XML에선 `<`, `&`를 그대로 못 써서 `&lt;`, `&amp;`로 저장한다.
제목에 `&`가 든 영상은 RSS에 `&amp;`로 들어있어, 되돌리지 않으면 화면에 `&amp;`가 그대로 보인다.
→ `decode()`가 처리. **`&amp;`를 마지막에 푸는 순서가 중요** (먼저 풀면 `&amp;lt;`가 꼬임).

## 5. 캐싱 — 두 종류

| 종류 | 위치 | 효과 |
|---|---|---|
| **엣지 캐시** | Worker가 유튜브를 부를 때 (`cf.cacheTtl`) | 영상 10분 / 핸들→ID 1시간 / 죽음 확인 5분. 유튜브 부담·속도 개선 |
| ~~**HTTP 캐시**~~ | ~~Worker 응답 (`max-age=600`)~~ | ⛔ **2026-08-21에 걷어냈다 → `no-store`.** 아래 |
| **localStorage 캐시** | 브라우저 | 재방문 시 **이전 결과를 즉시 그리고**, 뒤에서 조용히 갱신해 교체 → 체감 속도 급상승 |

### ⭐ 브라우저 HTTP 캐시를 왜 없앴나 (2026-08-21)

Worker 응답에 `Cache-Control: public, max-age=600`이 붙어 있었다. 주석에 적힌 의도는
*"같은 채널을 자주 부르면 캐시가 대신 답한다(유튜브 부담·속도)"*였는데, **근거 둘 다 이미 다른
층에 있었다**:

| 원래 노렸던 것 | 실제로 누가 하고 있었나 |
|---|---|
| 유튜브 부담 | **엣지 캐시**(`cf.cacheTtl`). 이 층이 없어도 유튜브까지 안 간다. 실측: 핸들 경로 1.20s → 0.47s (1.6MB를 통째로 건너뛴다) |
| 속도 | **localStorage 캐시**. 이 층이 아끼는 왕복 0.45초 동안 화면엔 이미 영상이 떠 있다 |

⭐ 게다가 **전제가 틀렸다**: 화면은 `claimLoad` 때문에 한 epoch에 채널당 **딱 한 번만** 부른다.
"자주 부르는" 일이 없으니 두 번째 호출을 위한 캐시가 발동할 자리 자체가 없다.
**실제로 발동하는 순간은 사용자가 새로고침했을 때** — 즉 *새 데이터를 달라*고 명시한 바로 그 순간이다.

→ 남는 순효과가 **"다시 물어보지 못하게 막는 것"뿐**이라 걷어냈다. (`90-gotchas.md` 26번)

⭐ 그리고 **판정마다 TTL을 달리 주던 것도 없앴다.** 캐시 지시는 이제 하나뿐이다 —
`no-store`. 수명을 달리 매기는 건 *"이 답은 틀릴 수 있으니 피해 시간을 깎자"*는 뜻이라
**틀린 답을 싸게 만들 뿐 답을 맞히지 못한다.** 맞히는 일은 `confirmGone`이 한다.

### 캐시 관련 필수 규칙 (실제로 데여서 얻음)

- **`Vary: Origin`** — 응답의 CORS 헤더가 Origin마다 다르므로 캐시도 Origin별로 갈라야 한다.
  없으면 localhost용 응답이 github.io 요청에 재사용돼 `Failed to fetch`.
  ⚠️ 지금은 `no-store`라 저장될 일이 없지만 **헤더는 남겨뒀다** — 캐시가 돌아오는 순간 다시 필수다.
- ~~**에러만 `no-store`**~~ → **전부 `no-store`** (2026-08-21). 그전엔 성공은 10분, 실패만
  안 굳혔다. `gone`·`empty`는 정상 응답(200)이라 10분 캐시를 탔는데, **그게 오진과 만나
  최악이 됐다** — 살아있는 채널이 "없어졌다"로 10분간 굳고 F5로도 안 풀렸다.
- 자세한 사고 기록: `90-gotchas.md` 10·11·26번

⚠️ **화면 쪽에 `fresh` 인자가 남아 있는 이유** (`lib/worker.ts`): 손으로 「↻ 다시 불러오기」를
누르면 `fetch(url, { cache: "reload" })`로 브라우저 캐시를 건너뛴다. **새 Worker 상대로는
이게 무의미하다**(어차피 `no-store`). 그래도 남긴 건 Worker가 손으로 붙여넣는 것이라
**옛 Worker가 살아 있는 기간**이 있기 때문이다 — `verified`와 같은 이유다.
옛 Worker가 완전히 사라지면 이 인자도 같이 지운다.

## 6. 실패를 다루는 태도

- `src/screens/Feed.tsx`: 채널별로 따로 fetch → 하나 실패해도 그 칸만 "불러오기 실패"로 표시.
- (옛 `collect.py`도 채널마다 `try/except`로 9개 중 1개 실패해도 나머지 8개는 나오게 짰었다 —
  경로가 바뀌어도 **부분 실패 격리라는 태도는 그대로 이어진다**.)
- **원칙**: 남의 서비스는 반드시 가끔 실패한다고 가정하고, 부분 실패를 격리한다.

### ⭐ 실패의 종류를 가른다 (2026-08-16)

부분 실패를 격리하는 것만으로는 부족했다. **무엇이 실패였는지도 갈라야 했다.**

`rss-proxy.js`가 모든 예외를 `catch`로 받아 502 하나로 뭉개고 있었다. 그래서
"채널이 삭제됐다"·"공개 영상이 0개다"·"유튜브가 아프다"가 화면에서 **구분 불가능**했다.

| 갈래 | 답 | 재시도 의미 |
|---|---|---|
| 채널 삭제·정지 **확인됨** | `200 { state: "gone", name: null, verified: true }` | ❌ 계속 죽어 있다 → **지워라** |
| 영상 0개 (살아있음) | `200 { state: "empty", name }` | ❌ 정상이다 → 그냥 두면 된다 |
| 핸들 오타 | `404 { error }` | ❌ 입력이 틀렸다 |
| 유튜브 5xx·네트워크 | `502 { error }` | ✅ **여기만 재시도가 의미 있다** |
| **모른다** (2026-08-21 신설) | `502 { error }` | ✅ 확인을 못 했을 뿐이다 → 다시 물어라 |

- **판정 기준은 상태코드다.** `getText`가 `e.upstream = res.status`를 실어 던지고,
  부르는 쪽이 `404`(답)와 그 외(고장)를 가른다. 메시지 문자열을 파싱하지 않는다.
- ⭐ **5xx를 "답을 모르겠다"에만 쓰기로 하니 상태코드가 뜻을 갖게 됐다.** 그전엔
  502를 봐도 서버를 의심해야 할지 채널을 의심해야 할지 알 수 없었다 — 08-05에
  실제로 "319개 동시 요청 과부하"를 의심하며 시간을 썼다(90-gotchas 20).

### ⭐ 그리고 판정에 "모른다"를 만들었다 (2026-08-21)

08-16의 갈래는 **알아냈다 / 못 알아냈다** 둘뿐이었고, "알아냈다"에 **틀릴 수 있는 답**이
섞여 있었다. RSS의 404를 그대로 삭제로 믿은 것이다. → 살아있는 채널 40개가 전부
"없어졌어"로 떴다. 자세한 것은 `20-rss-and-channel-id.md` 4절.

⭐ **증명 못 한 것을 사실로 단정하지 않는다** — 이게 이번에 늘어난 규칙이다.
502는 이제 *"장애다"*가 아니라 *"확정된 답을 못 준다"*를 뜻한다(장애는 그 부분집합).

## 7. XSS 방지

영상 제목을 화면에 넣을 때 `innerHTML`이 아니라 **`textContent`**를 쓴다.
제목에 `<script>`가 들어있어도 글자로만 취급돼 실행되지 않는다.
→ 남이 만든 데이터를 화면에 넣을 땐 항상 이렇게.
