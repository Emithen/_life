# 겪은 함정들 (실제로 터진 것만)

> 기준: youtube-feed `ef18e3a` · 2026-08-04
> 전부 실제로 겪고 고친 것. 같은 실수를 반복하지 않으려고 남긴다.

## 1. `.gitignore`가 배포 결과물을 삼켜 404 (2026-07-24)

`actions-gh-pages`가 `publish_dir: .`을 올릴 때 **저장소의 `.gitignore`를 그대로 따른다.**
→ `index.html`을 무시하면 사이트에서 빠져 **404**.

- **그래서**: 사이트에 필요한 파일은 생성물이라도 **추적한다**(커밋한다).
  당시엔 `index.html`·`data.json`이 대상이었다.
- `youtube-feed/.gitignore`에 이 경고가 주석으로 박혀 있다. 지우지 말 것.
- **2026-07-31 이후 대상이 넓어졌다** — `app.js`가 `src/`로 들어갔으므로
  `src/`를 무시하면 사이트에서 통째로 빠진다. 폴더를 새로 만들 때마다 이 함정이 되살아난다.
- 정석 해법(나중에): 생성물이 다시 생기면 출력을 `dist/`로 보내고 `publish_dir: dist`로 분리.
  지금은 저장소에 손으로 쓴 원본만 있어 급하지 않다(`data.json` 삭제로 생성물이 없어짐).

## 2. 모바일 버전 불일치 — 캐시 (2026-07-28)

폰에서 `Cannot read properties of null (reading 'replaceChildren')`.
원인: **새 `index.html` + 캐시된 옛 `app.js`** 조합. 옛 코드가 사라진 `#app`을 찾다 터짐.

- **해결**: `<script src="src/app.js?v=10">` — 캐시 버스팅. **`app.js` 고칠 때 숫자를 올린다.**
  (경로가 `src/`로 바뀐 2026-07-31에 `v=10`. 경로가 바뀌면 URL이 달라져 캐시는 자동으로 갈리지만,
  규칙을 예외 없이 지키는 편이 헷갈리지 않는다.)
- 추가 방어: `app.js`가 대상 엘리먼트 없으면 크래시 대신 조용히 스킵.
- 실무에선 빌드 도구가 파일명에 해시를 붙여 자동화하는 영역.

**2026-07-31 모듈 분리로 이 함정의 면적이 넓어졌다** (아직 안 당했지만 구조가 똑같다):
`<script type="module" src="src/app.js?v=13">`의 `?v=`는 **app.js에만** 붙는다.
`import "./worker.js"`는 쿼리 없이 요청되므로 **새 app.js + 캐시된 옛 worker.js** 조합이 나올 수 있다
— 위에서 실제로 겪은 사고와 정확히 같은 모양이다.

- **그래서**: import 경로에도 같은 버전을 단다 → `import {...} from "./worker.js?v=13"`
- 버전 올릴 곳이 **4군데**다: `index.html` 1곳 + `app.js`의 import 3곳
  (`worker.js`·`storage.js`·`youtube.js`). 모듈이 늘 때마다 이 숫자가 커진다 — 하나라도 빠지면 위 사고가 난다.
- 교훈: **"버전을 손으로 여러 곳에 맞추는 상태"는 오래 못 간다.** 이게 귀찮아지는 순간이
  빌드 도구를 들일 신호다(파일명 해시를 자동으로 붙여준다). 지금은 파일 3개라 감당된다.
- 곁가지: 모듈은 `file://`로 안 열린다(CORS). 확인은 반드시 로컬 서버로.
  함수도 더 이상 전역이 아니라 콘솔에서 직접 못 부른다 — 디버깅은 화면 조작으로.

## 8. 채널 페이지에서 엉뚱한 채널 ID를 집음 — **4번의 재발** (2026-07-28)

Worker에서 `@핸들 → channel_id`를 찾을 때 **첫 `"channelId"`**를 집었더니 추천 채널이 잡혔다.

- **해결 순서**: `rel="canonical"` 링크(페이지의 진짜 주인) → `"externalId"` → `"channelId"`(최후)
- 교훈: 4번과 **정확히 같은 실수를 5일 만에 반복**했다. 남의 HTML에서 값을 뽑을 땐
  "먼저 나오는 것"이 아니라 **"의미상 권위 있는 것"**을 골라야 한다.

## 9. Worker CPU 한도 초과 → `Failed to fetch` (2026-07-28)

유튜브 채널 페이지는 **2.4MB**. 정규식으로 전체를 훑으니 Worker CPU 한도(10ms)를 넘겨 죽었고,
그 경우 Cloudflare가 CORS 헤더 없는 에러 페이지를 반환해 브라우저엔 `Failed to fetch`로 보인다.
- **해결**: `indexOf`(네이티브 검색)로 위치만 찾고 그 뒤 40글자만 정규식 검사.
- 교훈: 큰 문자열에 정규식을 함부로 돌리지 않는다. `Failed to fetch`는 **CORS 헤더가 없는 응답**의 증상이기도 하다.

## 10. `Vary: Origin` 누락 — 캐시가 CORS를 깨뜨림 (2026-07-28)

응답의 `Access-Control-Allow-Origin`은 요청 Origin마다 다른데 `Vary: Origin`이 없었다.
→ **localhost에서 만든 응답이 캐시되어 github.io 요청에 재사용** → ACAO 불일치 → `Failed to fetch`.
- **해결**: `Vary: Origin` 추가.
- 함께: 에러 응답은 `Cache-Control: no-store`. 안 그러면 일시적 장애가 10분간 굳는다.
- 교훈: **응답 헤더가 요청에 따라 달라지면 반드시 `Vary`를 붙인다.**

## 11. 수정 직후의 "안 고쳐졌는데?" 착시 (2026-07-28)

Worker를 고쳐 배포했는데 브라우저에선 여전히 옛 결과가 나왔다.
- 원인 ①: 응답 `max-age=600` 때문에 **브라우저가 10분간 옛 응답을 보관**. (`{cache:"reload"}`로 확인 가능)
- 원인 ②: Cloudflare 배포 **전파에 ~20초**. 배포 직후 즉시 확인하면 옛 코드가 응답한다.
- 교훈: 배포 직후 검증은 **캐시 우회 + 잠깐 대기** 두 가지를 챙긴다.

## 14. 잘린 재생목록 ID — 코드는 멀쩡한데 실패 (2026-07-31)

하이픈 등에서 선택이 끊겨 앞부분만 잡히는 일이 잦다 (제보된 값 13자, 정상은 18자/34자).

- **해결 ②**: 실패가 "찾을 수 없음" 계열이면 **실제 사용한 ID와 그 길이**를 메시지에 함께 띄우고,

- 교훈: "안 된다"는 제보를 받으면 **먼저 내 코드를 의심하지 말고 입력값을 재현**해본다.
  그리고 원인을 나만 아는 것으로 끝내지 말고, **에러 메시지가 스스로 원인을 말하게** 만든다.

## 15. OAuth 첫 로그인이 `access_denied`로 막힘 (2026-07-31)

클라이언트 ID·승인된 원본을 다 넣었는데 로그인 창이 이렇게 떴다:
**"액세스 차단됨: emithen.github.io은(는) Google 인증 절차를 완료하지 않았습니다" · `403 access_denied`**

원인은 **테스트 사용자 미등록**. 앱이 "테스트 중" 상태면 개발자가 승인한 계정만 들어갈 수 있는데,
정작 내 계정을 명단에 안 넣었다. → OAuth 동의 화면 → 테스트 사용자에 본인 Gmail 추가로 해결.

- **오류 화면이 진단을 절반 해준다**: 이 메시지가 떴다는 건 구글이 **앱을 찾아 테스터 명단까지 조회했다**는 뜻,
  즉 **승인된 JavaScript 원본은 정상**이라는 신호다. 원본이 틀렸으면 `origin_mismatch`가 뜬다.
  → OAuth 오류는 "무엇이 실패했나"보다 **"어디까지 갔나"**를 읽어야 빨리 잡힌다.
- **프로젝트를 헷갈리면 증상이 똑같다.** 클라이언트 ID 앞의 숫자가 그대로 **클라우드 프로젝트 번호**다
  (`60100393090-...` → 프로젝트 번호 `60100393090`). 콘솔에서 이 번호부터 맞춰놓고 손댄다.
- 테스트 모드로 계속 둬도 된다. 알려진 제약인 **refresh token 7일 만료는 우리와 무관**하다 —
  브라우저 토큰 플로우라 refresh token을 애초에 안 받는다.

## 16. Cloudflare에 **엉뚱한 파일**을 붙여넣어 Worker가 통째로 죽음 (2026-07-31)

일원화 배포 중 Worker의 모든 경로가 404가 됐다. 채널 추가가 `Failed to fetch`로 실패.
대시보드는 멀쩡해 보였다 — 라우트 켜짐, Active deployment 100%, **Error Rate 0%**.

원인: Cloudflare 에디터에 `worker/rss-proxy.js`(진짜 Worker)가 아니라
**`src/worker.js`(브라우저에서 Worker를 *부르는* 쪽)** 를 붙여넣었다.
그 파일엔 `export default { fetch }`가 없어서 **요청을 받을 핸들러가 없는 상태**가 됐고,
Cloudflare가 자기 기본 404 HTML을 돌려줬다. 미리보기 창에 답이 떠 있었다:
`The requested module 'worker.js' does not provide an export named 'default'`

- **`Error Rate 0%`가 오히려 결정적 단서였다.** 요청이 핸들러에 닿아 실패한 거라면 에러율이 올라간다.
  0%라는 건 **요청이 Worker까지 아예 안 갔다**는 뜻 → 코드가 아니라 "핸들러/라우팅"을 의심해야 한다.
- **헬스체크(`/`)가 진단을 반으로 줄인다.** 파라미터도 키도 필요 없는 경로가 404면 코드 문제가 아니다.
  `/`가 살아 있고 `usage`에 `/rss` 하나만 나오면 지금 코드가 맞다.
- 이건 **15번과 같은 독법**이다 — 오류를 "무엇이 실패했나"가 아니라 **"어디까지 갔나"**로 읽는다.
  두 번 연속 이 방법으로 잡았으니 기본기로 삼는다.
- `Failed to fetch`로 보인 이유는 9·10번과 동일 — Cloudflare 404 HTML엔 **CORS 헤더가 없다.**

### 왜 헷갈렸나 (이름이 함정이었다)

`src/worker.js`(부르는 쪽)와 `worker/rss-proxy.js`(진짜 Worker)가 둘 다 "worker"다.
게다가 **Cloudflare 에디터의 탭 이름이 `worker.js`** 라서 "worker.js를 붙여넣으면 되겠지"가 자연스러웠다.

- `src/relay.js`로 개명하는 안이 있었으나 **하지 않기로 했다**(2026-07-31 판단).
  → 이름은 그대로이므로 **붙여넣기 전에 이 두 줄을 눈으로 확인한다**:

```js
export default {
  async fetch(request) {
```

이게 없으면 Worker가 아니라 브라우저 모듈이다. **`export default`가 곧 "이건 Worker다"의 표식.**

## 17. 두 기기에서 갈라진 브랜치 — **나중에 커밋한 쪽이 더 낡을 수 있다** (2026-08-04)

`git pull`이 `fatal: Need to specify how to reconcile divergent branches`로 멈췄다.
`youtube-feed`와 `_life` **두 저장소에서 동시에** 터졌다. 원인은 같다 —
한 기기에서 커밋·푸시한 뒤, 다른 기기에서 **fetch 없이** 그 위가 아닌 옛 커밋 위에 새로 쌓았다.

- 갈라짐 자체는 정상이고, git은 합치는 방법(merge/rebase)을 못 정해서 물어본 것뿐이다.
- 진짜 함정은 **어느 쪽이 최신인지 착각한 것**이었다:

| | 커밋 시각 | 실제 내용 |
|---|---|---|
| 로컬 `427073c` | 08-03 15:13 | **더 낡았다** — 08-02 커밋을 못 받은 상태에서 쓴 글 |
| 원격 `4af2eb7` | 08-02 06:41 | 더 최신 — 로컬이 쓴 내용을 이미 포함하고 더 나아감 |

⭐ **커밋 시각은 최신성이 아니다. "어느 커밋 위에 얹혔는가"(부모)가 최신성이다.**
두 커밋의 부모 blob이 `5d152b7`로 같았던 게 결정적 증거였다 — **같은 원본에서 각자 고쳤다**는 뜻.

- 확인 명령: `git log --oneline origin/main..main`(로컬만) / `git log --oneline main..origin/main`(원격만)
- 합치기 전에 **충돌 지점을 미리 볼 수 있다**: `git merge-tree --write-tree main origin/main`
  → 작업트리를 건드리지 않고 CONFLICT 여부만 알려준다. 겁먹지 않고 판단하는 데 도움이 된다.
- 이번엔 로컬을 버리고 원격을 택했는데, **로컬에만 있던 정정 3건은 따로 이식**해야 했다.
  "어느 쪽을 택한다"가 아니라 **"각자 고유한 게 뭔지 세어본다"**가 먼저다.

## 18. 문서에 박은 **기준 커밋이 사라진 커밋**을 가리킴 (2026-08-04)

`docs/core/`의 각 문서 머리에 `> 기준: youtube-feed <해시>`를 박아둔다(낡으면 갱신하라는 캐시 무효화 장치).
그런데 17번에서 로컬 커밋 `427073c`를 폐기하자, **그 해시를 기준으로 적어둔 `_life` 커밋이
존재하지 않는 커밋을 가리키게** 됐다. 문서는 아무 일도 안 일어난 채 조용히 거짓말을 한다.

- 이 방식의 대가다. 해시를 박으면 정확해지는 대신 **그 커밋이 사라질 때 같이 썩는다.**
- 규칙: **기준 해시는 푸시된 커밋만 쓴다.** 로컬에만 있는 커밋을 기준으로 문서를 갱신하지 않는다.
- 저장소가 2개(`_life`↔`youtube-feed`)라 더 잘 어긋난다 — 한쪽 해시를 다른 쪽 문서가 들고 있는 구조다.

## 19. "이건 로컬 설정이니까"라고 단정하고 gitignore할 뻔함 (2026-08-04)

로컬 확인용 `.claude/launch.json`을 만들면서 **절대경로가 박혀 있으니 기기별 파일**이라 판단하고
`.gitignore`에 넣었다. 그런데 원격엔 **이미 같은 파일이 커밋돼 있었고**(`3a73c6a`),
그쪽은 `--directory youtube-feed`처럼 **상대경로로 짜서 일부러 공유하게** 만든 것이었다.

- 기기별로 만든 건 **원격 파일이 아니라 내가 방금 쓴 파일**이었다. 판단 근거가 자기 자신이었던 셈.
- 규칙: 어떤 파일을 "로컬 전용"으로 분류하기 전에 **원격이 이미 어떻게 다루고 있는지 본다** —
  `git log --oneline origin/main -- <경로>` 한 줄이면 끝난다.
- 덤: 그 공유 파일이 이 맥에선 안 돌았다. `runtimeExecutable: "python"`인데
  **macOS엔 `python`이 없다**(`python3`만). 공유 설정은 **다른 기기에서 실제로 실행해봐야** 공유가 된다.

## 20. 502를 "부하"로 오진 — 부하와 결정적 실패는 **재현성**으로 갈린다 (2026-08-05)

콘솔에 `502 Bad Gateway`가 채널 3개에서 떴다. 마침 드라이브에서 구독 채널 **319개**를
막 받아온 직후였고, `renderMyChannels`가 `await` 없이 `.then()`만 붙여 **전부 동시에** 쏘는
구조라 "동시 요청 과부하"로 읽혔다. 그럴듯했다 — 319개 중 3개만 실패한 것도 레이트리밋처럼 보였다.

**틀렸다.** 실제로 쳐보니 셋 다 재현되는 결정적 실패였다:

| 채널 | 유튜브 RSS 직접 | Worker | 실제 |
|---|---|---|---|
| `UCo7Kl08…` | **404** | `유튜브 응답 404` | 채널이 없어짐(삭제/정지) |
| `UCQ5rBuSDZ…` | 200 | `영상을 못 찾았어` | 피드는 살아있고 **공개 영상 0개** |
| `UCPr1OujAE…` | 200 | 같음 | 같음 |

⭐ **판별법**: 부하 문제면 **새로고침마다 실패하는 대상이 달라진다.**
결정적 실패는 **같은 것이 항상 같은 이유로** 실패한다. 이걸 먼저 봤으면 병렬 구조를
의심하는 데 시간을 안 썼다. 확인은 명령 한 줄이면 된다:

```bash
curl -s "https://yt-rss.javer1155.workers.dev/rss?ch=<채널ID>&limit=6"
curl -s -o /dev/null -w "%{http_code}" "https://www.youtube.com/feeds/videos.xml?channel_id=<채널ID>"
```

**⚠️ 더 큰 교훈: 원인을 잘못 짚으면 해법도 잘못 나온다.**
이때 이미 "동시 실행 제한"과 "페이지 분할"을 *502 해법*으로 기획하고 있었다.
둘 다 그 자체로는 쓸모 있을 수 있지만 **이 문제의 해법은 아니었고**, 그대로 갔으면
문서에 틀린 인과가 박혔을 것이다. → 선별(구독≠피드)의 근거는 **성능이 아니라 기획**이다.
319개 병렬이 실제로 문제인지는 **아직 모른다**(징후 없음).

**진짜 결함은 에러 계약이었다.** `worker/rss-proxy.js`가 `catch (e) → json({error}, 502)`로
**모든 예외를 502로 뭉갠다.** 위 셋은 전부 정상적인 사용자 상황인데 "게이트웨이 고장"으로
보고된다. `src/worker.js`엔 이미 `err.notFound` 판정이 있는데 502라서 그 길로 가지도 않는다.
→ 고칠 모양은 **채널 404 → `notFound` / 영상 0개 → 200 + 빈 목록 / 나머지만 502**.
→ 설계는 `40-screens-and-ui.md` 4절.

## 21. `silent` 로그인이 조용하지 않다 — 새로고침마다 팝업 (2026-08-15)

**증상**: 새로고침할 때마다 구글 로그인이 재시도되고, 콘솔에 이게 계속 쌓인다.

```
[GSI_LOGGER]: Failed to open popup window on url: https://accounts.google.com/... Maybe blocked by the browser?
```

**원인**: 페이지가 열릴 때마다 `yt.signIn({ silent: true })`를 무조건 한 번 시도하고 있었다.
GIS의 `prompt: ""`(= silent)는 **동의 화면만** 건너뛴다 — **팝업 창은 그대로 연다.**

⭐ **틀린 건 코드가 아니라 그 코드를 낳은 전제였다.** 원래 설계는
"토큰을 메모리에만 두고 **열 때 조용히 재발급받는 편이 안전하다**"였는데,
조용한 재발급이 공짜라는 그 가정이 사실이 아니었다.
→ 자동 시도를 없애고 토큰을 `localStorage`에 살린다. 필요한 동작을 누를 때만 로그인.

⚠️ **이 경고를 몇 주 동안 무해한 잡음으로 넘겼다.** 로그인은 어차피 되니까.
   콘솔에 매번 나는 에러는 "무해해 보여도" 그 자체가 증상이다.

⚠️ 토큰 키(`authToken`)는 **`storage.js`의 KEYS에 넣지 않는다.**
   넣으면 `exportAll()`에 실려 **드라이브로 올라간다.** 한 줄 실수로 날 사고라 자리를 분리했다.

## 22. **한 번도 참이 된 적 없는 판정** — 문자열로 에러를 가르면 조용히 틀린다 (2026-08-16)

**증상**: 없다. 그게 문제였다.

`src/worker.js`의 `get()`이 실패를 이렇게 분류하고 있었다:

```js
err.notFound = res.status === 404 || /찾을 수 없|not ?found/i.test(err.message);
```

**원인**: 두 조건 다 절대 안 맞았다.

| 조건 | 실제 |
|---|---|
| `res.status === 404` | Worker는 모든 예외를 **502**로 뭉갰다 → 404가 나올 수 없었다 |
| `/찾을 수 없\|not ?found/i` | Worker가 내는 말은 `"못 찾았어"`·`"채널 ID를 못 찾았어"` — **글자가 다르다** |

즉 이 값은 **배포 이후 한 번도 `true`가 된 적이 없다.** 게다가 읽는 곳도 없었다 —
유일한 소비자(`app.js`의 재생목록 안내)는 `youtube.js`가 만든 에러를 본다.
`worker.js` 머리엔 "판정만 넘긴다"는 설계 선언이 적혀 있었는데, **그 판정이 죽어 있었다.**

⭐ **틀린 코드가 아니라 아무 일도 안 하는 코드였다.** 버그는 보통 잘못된 동작으로
드러나는데, 이건 "쓰이지 않는 분기"라 증상이 아예 없다. 문서·주석은 계속 그게
동작한다고 말하고 있어서 **읽는 사람이 틀린 그림을 갖게 된다.**

⭐ **판정은 상태코드로 한다. 메시지 문자열로 하지 않는다.**
문자열 판정은 ⓐ 메시지를 고치는 순간 조용히 깨지고 ⓑ 깨져도 아무도 모른다.
에러 계약을 갈라 상태코드가 뜻을 갖게 된 뒤로는 `res.status === 404` 한 줄이면 된다.

⚠️ **같이 배운 것**: 판정을 만들 때 **그걸 읽는 쪽을 같이 만들지 않으면** 검증되지 않는다.
쓰는 곳 없이 넘겨만 두면 맞는지 틀린지 확인할 계기가 영영 안 온다.
→ 07-28의 "선별 없는 기능은 안 쓰인다"와 같은 모양이다. **소비자가 없는 생산은 검증되지 않는다.**
