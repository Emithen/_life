# 데이터 흐름과 계약(contract)

> 기준: youtube-feed `0ed3e06` · 2026-08-17

## 1. 두 경로가 근본적으로 다른 이유

**"미리 만들어두기 vs 그때그때 만들기"** — 웹 아키텍처의 핵심 트레이드오프.
이 프로젝트엔 둘 다 구현돼 있었고, **2026-07-28 현재는 경로 B만 살아 있다**
(경로 A는 "지금 필요 없다"고 판단해 07-28에 중단, 07-31에 파일도 삭제 — 되살리려면
`collect.yml` 주석을 푸는 것만으론 안 되고 **git 이력에서 `collect.py`부터 꺼내야** 한다).
파일은 지웠지만 **비교 자체가 학습 자산이라 설명은 남겨둔다.** 아래 경로 A는 "이랬었다"는 기록이다.

### 경로 A · 추천 채널 (미리 만들어둠) — 🅾️ 현재 중단

```
[cron 3시간마다 / main push]
   → GitHub Actions에서 collect.py 실행
   → 채널 9개 RSS 순회 수집
   → data.json 파일로 저장 → gh-pages 게시
[사용자]
   → 사이트 열면 data.json 하나만 받으면 끝
```

- **장점**: 빠름. 유튜브가 느려도 사용자는 영향 없음. CORS 문제 없음(서버끼리 통신이라).
- **단점**: 실시간 아님(최대 3시간 지연). 채널 목록이 코드에 박혀 있어 사용자가 못 바꿈.

### 경로 B · 내 채널 (그때그때 만듦) — ✅ 현재 유일한 경로

```
[사용자가 채널 추가]
   → localStorage에 {topic, name, channelId} 저장
[사이트 열 때마다]
   → 저장된 채널마다 지금 유튜브에서 RSS 가져옴 (릴레이 경유)
   → 화면에 그림 + 결과를 localStorage에 캐시
```

- **장점**: 사용자마다 다른 채널. 서버·계정 없이 개인화.
- **단점**: 느림. 남의 서비스(유튜브·릴레이)에 실시간 의존 → 실패 가능. 한 기기에만 저장됨.

> 한때 두 경로를 화면에서 **같은 모양으로 합쳐서** 보여줬다(내 채널 위, 추천 채널 아래).
> 합칠 수 있었던 이유가 아래의 "계약" 덕분이다 — 경로 A를 되살려도 화면 코드는 거의 그대로다.

### 경로 C · 나중에 볼 풀 (한 번 담아두고 계속 씀) — ✅ 2026-07-31 추가

랜덤 추천용. 앞의 둘과 성격이 다르다 — **매번 가져오는 게 아니라 한 번 가져와 쌓아두고 재사용**한다.

```
[가져오기: 둘 중 아무거나, 여러 번 해도 됨]
   ① WL 화면에서 뽑은 영상 ID 붙여넣기 → videos.list (50개씩 나눠서)
   ② watchme 재생목록 동기화        → playlistItems.list (전체 페이지 순회)
   ※ 둘 다 **로그인 필요**(2026-07-31 일원화). 대신 비공개 재생목록도 읽힌다.
   → 둘 다 같은 모양의 videos[]를 돌려줌 → laterPool에 병합(id 기준 중복 제거)
[추천할 때]
   → 네트워크 없이 laterPool에서 무작위 1개 (본 영상은 후보에서 제외)
```

- **왜 이 모양인가**: 유튜브 "나중에 볼"(WL)은 2016-09-12부터 API·RSS 모두 막혀 있다.
  → 목록을 실시간으로 읽어올 방법이 없으니 **"옮기지 않고 가져온다"**로 전제를 바꿨다.
- 그래서 풀은 **한 번 채우면 브라우저에 남는 자산**이다(`laterPool`). 추천은 오프라인에서도 된다.
- 대신 유튜브 쪽에서 지운 영상은 자동으로 사라지지 않는다 — 동기화를 다시 돌려야 반영된다.

## 2. 계약(contract)이란 무엇이고 왜 하는가

**계약 = "데이터가 어떤 모양일지"에 대한 약속.** 이 약속만 지키면 양쪽은 서로를 몰라도 된다.

### 진화 과정

| 단계 | 계약의 단위 | 문제 |
|---|---|---|
| v0 이전 | 없음. `collect.py`가 HTML 문자열을 통째로 만듦 | 화면 고치려면 파이썬을 건드려야 함 |
| **v0** (07-26) | `template.html`의 `{{TITLE}}`·`{{BODY}}` 토큰 | 계약 단위가 "문자열 조각"이라 거칢. `<h2>/<a>` 구조를 여전히 파이썬이 쥠 |
| **v1** (07-28, 현재) | **데이터 구조(JSON)** | 파이썬이 HTML을 완전히 모름 ✅ |

### v1의 계약 — `data.json`의 모양

```json
{
  "updated": "2026-07-28 16:41",
  "sections": [
    { "topic": "체스", "name": "체스프릭",
      "videos": [ { "title": "...", "link": "...", "date": "2026-07-22" } ] }
  ]
}
```

- `collect.py` → 이 모양만 뱉는다. HTML 태그를 하나도 모른다.
- `app.js` → 이 모양만 읽어 그린다. 파이썬을 하나도 모른다.
- 둘 사이 의존성이 **JSON 파일 한 장으로 완전히 끊긴다.**

### Worker도 같은 모양을 쓴다 (의도된 설계)

```
GET /rss?ch=<채널ID|@핸들|URL>&limit=6
→ { "channelId": "UC...", "name": "채널명",
    "videos": [ { "id": "2-3F7y5AKJw",              ← 영상 식별(본 영상 기록용)
                  "title": "...", "link": "...",
                  "date": "2026-07-29",              ← 화면 표시용(날짜만)
                  "published": "2026-07-29T03:00:37+00:00" } ] }  ← 24시간 계산용
```

`data.json`의 `sections` 한 칸과 **같은 모양**. 그래서 화면은 추천 채널이든 내 채널이든
**같은 렌더 함수 하나로** 처리한다.

#### 실패도 이 계약의 일부다 (2026-08-16)

```
200 { channelId, name,       videos: [...] }               정상 — 위 모양 그대로
200 { channelId, name,       videos: [], state: "empty" }  살아있는데 공개 영상 0개
200 { channelId, name: null, videos: [], state: "gone"  }  채널 404 — 삭제·정지
404 { error }   입력을 채널로 해석 못 함 (@핸들 오타)
502 { error }   진짜 장애 — 유튜브 5xx·네트워크
400 { error }   ch 파라미터 없음
```

⭐ **"죽었다"는 실패가 아니라 답이다.** 채널이 삭제됐다는 것은 릴레이가 **성공적으로
알아낸 사실**이지 릴레이의 고장이 아니다. 그래서 200으로 준다. 5xx는 **"답을 모르겠다"**
일 때만 쓴다 — 그러면 **상태코드가 곧 "재시도해도 되나"의 답**이 된다.

그전엔 이 셋(채널 404 · 영상 0개 · 유튜브 5xx)이 전부 `502` 한 덩어리였다.
2026-08-05에 502의 원인을 규명하고도("정상 상황이 서버 고장으로 보고되고 있었다")
계약은 안 고쳤는데, 구독 319개에서 죽은 채널을 골라내려니 **그게 정확히 막는 벽**이었다.
→ 진단과 계약 수정 사이의 11일이 그대로 비용이 됐다.

⭐ **정상 응답은 한 글자도 안 바뀌었다**(`state` 없음 = 정상). 07-30에 `id`·`published`를
추가할 때 쓴 규칙("기존 필드는 두고 추가만"), 저장 채널의 `active`("필드 없음 = 켜짐"),
백업 payload와 **전부 같은 규약**이다. 이 규약의 보상이 여기서 또 나왔다 —
Worker는 Cloudflare 대시보드에 손으로 붙여넣는 것이라 화면과 배포가 따로 노는데,
**어느 쪽을 먼저 배포해도 안 깨진다.**

⚠️ 부수 효과: **영상 0개 채널이 이제 추가된다.** 살아있는 채널이라 막을 이유가 없었는데
502가 "고장"처럼 보이게 만들어 거부되고 있었다. **오진 하나가 기능 하나를 막고 있었다.**

### 풀을 채우는 두 호출도 같은 `videos[]`를 준다

```
fetchPlaylist(id)   ← 전체 순회(최대 1000개), YouTube Data API playlistItems.list
→ { playlistId, count: 355, skipped: 3,
    videos: [ { id, title, link, date, published, channel } ] }

fetchVideos(ids)    ← 최대 50개(= API 1회 호출 = 1 unit), videos.list
→ { count: 50, missing: ["xxxxxxxxxxx"],
    videos: [ { id, title, link, date, published, channel } ] }
```

⚠️ 이 둘은 **2026-07-31에 Worker(`/playlist`·`/videos`)에서 `src/lib/youtube.ts`로 옮겨갔다.**
모양은 그대로다 — 그래서 화면 코드가 안 바뀌었다. 자세히는 아래 "같은 계약, 다른 출처".

- `videos[]`의 모양은 `/rss`와 **같다**. 다만 풀에는 **여러 채널이 섞이므로** `channel`(채널명)이 하나 더 붙는다.
  → 채널별 목록에선 채널명이 제목 위에 한 번만 나오면 되지만, 풀에선 영상마다 필요하다.
- **"못 가져온 것"도 계약에 넣었다** — `/videos`의 `missing`(요청했는데 안 돌아온 ID),
  `/playlist`의 `skipped`(비공개·삭제라 건너뛴 개수). 조용히 사라지면 사용자가
  "왜 516개 넣었는데 500개지?"를 알 수 없다. **빠진 이유를 셈해서 돌려주는 것도 계약의 일부.**
- 50개 넘는 ID는 **호출자가 나눠서** 부른다(`fetchVideosChunked`. ⚠️ 이 함수는 2026-08-07에 기능과 함께 삭제됐다 — git 이력에 있다).
  50개는 Data API가 정한 한도다 — 한도는 서버가 정하고, 쪼개는 책임은 호출자가 진다.

### 계약의 화면 쪽 끝은 `src/lib/worker.ts` 하나다 (2026-07-31 모듈 분리)

계약은 양쪽에 끝이 있다. Worker 쪽은 `worker/rss-proxy.js`, **화면 쪽은 `src/lib/worker.ts`**.
예전엔 화면 쪽 끝이 세 군데로 흩어져 있었고(그중 둘은 버튼 핸들러 안), 응답 해석 4줄이 복사돼 있었다.

```ts
// src/lib/worker.ts — 2026-07-31 일원화 이후 이것 하나만 남았다. 화면은 URL을 모른다.
export const fetchChannel = (ch: string) => get<ChannelFeed>("/rss", { ch, limit: String(LIMIT) });
```

> ⭐ **이 분리의 값이 2026-08-17 React 이식에서 청구됐다.** DOM을 아는 파일이
> `app.js` 하나뿐이라 `lib/` 넷(storage·youtube·drive·worker, 약 590줄)은
> **로직을 한 줄도 안 바꾸고** 타입만 붙여 건너왔다. 버린 건 화면 조립 780줄뿐이다.
> 계약의 값어치는 "한쪽을 갈아치울 때" 청구된다 — 07-31 OAuth 이사에 이은 **두 번째 청구**다.
> ⚠️ 이때도 규칙은 같았다: **프레임워크와 동작을 같이 바꾸지 않는다.** 둘을 함께 바꾸면
> 뭐가 깨졌는지 알 수 없다(08-05 컬러 토큰의 "보이는 변화 0을 측정해 확인"과 같은 규칙).

- **에러도 계약이다** — `get()`이 `err.notFound` 같은 **판정**만 붙여 넘기고,
  한국어 문장은 화면이 만든다. 같은 실패라도 채널 추가와 재생목록 동기화는 할 말이 다르기 때문.
  - ⚠️ **판정은 상태코드로 한다. 메시지 문자열로 하지 않는다** (2026-08-16).
    `err.notFound`가 원래 `res.status === 404 || /찾을 수 없|not ?found/i.test(msg)` 였는데,
    Worker는 **항상 502**를 줬고 메시지는 `"못 찾았어"`라 정규식과 글자가 달랐다 —
    즉 **한 번도 참이 된 적이 없었다.** → 90-gotchas 22
  - 2026-08-17부터 이 계약은 **타입으로도 적혀 있다**(`src/lib/types.ts`).
    새 규칙이 아니라 **이 문서에 이미 글로 있던 것**을 컴파일러도 읽게 한 것이다.
    ⭐ `state?`가 optional인 게 핵심 — **"없음 = 정상"이 계약**이라서.
  - `state`는 에러가 아니라 **정상 응답에 실려 오는 판정**이다. `throw`로 오지 않으므로
    `catch`로는 절대 안 잡힌다. 화면은 `data.state`를 **따로 봐야 한다.**
- **서버가 정한 한도는 화면이 아니라 창구가 안다.** `CHUNK = 50`은 지금 `src/lib/youtube.ts`에 있다
  (Data API의 한도라서). 화면의 사정이 아니라 계약의 일부다.

### 같은 계약, 다른 출처 — 계약이 값을 한 순간 ⭐ (2026-07-31)

구글 로그인을 붙이면서 `src/youtube.js`(현 `src/lib/youtube.ts`)가 생겼다. 이 모듈의 `fetchPlaylist`·`fetchVideos`는
**`worker.js`가 주던 것과 글자 그대로 같은 모양**을 돌려준다. 덕분에 이사가 3단계로 끝났다:

```js
// 1단계 — 출처를 한 줄로 갈랐다 (OAuth 우선, 로그인 전엔 Worker 폴백)
const source = () => (yt.isSignedIn() ? yt : worker);

// 2단계 — 로그인 상태로 두 경로를 실제로 검증
// 3단계 — 폴백을 지우고 yt.* 직접 호출로 (source() 삭제, Worker 쪽 코드 146줄 제거)
```

- 데이터를 **어디서 가져오는지**가 통째로 바뀌었는데(내 서버의 API 키 → 사용자 본인 토큰)
  화면의 렌더·병합·랜덤 뽑기 코드는 **한 줄도 안 바뀌었다.**
- **1단계를 거친 게 핵심이다.** 곧바로 갈아치웠다면 검증 전에 돌아갈 길이 사라졌을 것이다.
  같은 모양이라 "두 출처를 동시에 살려두는 기간"을 공짜로 만들 수 있었다.
- 교훈: 계약의 값어치는 "한쪽을 갈아치울 때" 청구된다. 평소엔 그냥 번거로운 규칙처럼 보인다.

### 백업 파일도 계약이다 (2026-08-02)

지금까지의 계약은 전부 **바깥 → 화면** 방향이었다. 내보내기/가져오기는 방향이 다르다 —
**화면 ↔ 자기 자신**(다른 시점·다른 기기의 나)과의 계약이다.

```json
{ "version": 1,
  "exportedAt": "2026-08-02T...Z",
  "data": { "myChannels": [...], "watched": {...}, "laterPool": {...}, "playlistId": "PL..." } }
```

- **키를 localStorage와 똑같이 쓴다.** 파일을 열어보면 저장소와 같은 모양이라 대조가 쉽다.
- **`version`을 넣었다.** 앞의 계약들(`/rss` 등)은 "추가만 한다"로 버전 없이 버텼지만,
  백업 파일은 **몇 달 뒤의 파일이 돌아올 수 있다** — 그땐 모른다고 거절하는 게 조용히
  잘못 읽는 것보다 낫다. 계약 상대가 "미래의 나"라서 규칙이 달라지는 지점.
- **`channelCache`는 계약에서 뺐다.** Worker가 다시 만들어주는 것이라 옮길 가치가 없는데
  크기는 제일 크다. → *다시 만들 수 있는 것은 계약에 넣지 않는다.*
  - ⭐ **이 규칙이 2026-08-17에 두 번째로 쓰였다** — `subsCache`(구독 목록)도 같은 지위다.
    구독은 구글에 있는 것이고 우리는 고를 때 잠깐 보여줄 뿐이라, **저장이 아니라 캐시**다.
    구독을 *저장*했을 때 따라오던 두 가지가 이걸로 사라졌다:
    ⓐ 드라이브 payload에 319개가 실려 나갔다 ⓑ 유튜브에서 구독을 끊어도 유령처럼 남았다.
    실측: payload가 채널 37개 **2.8KB**, subsCache 19KB는 로컬에만.
  - ⭐ 규칙 하나가 두 번 값을 했다는 게 핵심이다. **"이건 저장인가 캐시인가"를 물어보는
    습관**이 생기면, 새 데이터를 들일 때마다 payload가 부는 것을 자동으로 막는다.
- **합치기 규칙도 계약의 일부다**: 기존 것이 이긴다(주제·이름·`addedAt` 보존),
  본 영상은 이른 시각을 남긴다. 그래서 두 기기에서 번갈아 가져와도 합집합이 되고 줄지 않는다.

> ⭐ **이 모양이 그대로 국면 B(기기 동기화)의 payload다.** 서버에 올릴 것도 받을 것도 이것이고,
> 바뀌는 건 `파일 ↔ 서버`뿐이다. 그래서 로그인 작업이 "새 설계"가 아니라
> **"`importAll`을 부르는 곳이 파일에서 네트워크로 바뀌는 일"**로 줄어든다.
> 계약을 먼저 만들어두면 다음 큰 작업이 작아진다는 것의 세 번째 사례.

> **계약을 넓힐 땐 기존 필드를 그대로 두고 추가만 한다** (2026-07-30에 `id`·`published`를 이렇게 추가).
> 그래야 구버전 화면이 새 응답을 받아도 안 깨진다.
> 반대로 화면 쪽엔 **폴백**을 둔다 — `id`가 없으면 링크에서 뽑아낸다.
> 덕분에 Worker와 화면의 **배포 순서가 달라도 안전**하다 (둘은 따로 배포된다).

## 3. 계약을 밖에 꺼낸 보상

- 화면(FE)을 마음껏 두껍게 만들어도 데이터 쪽은 무사하다.
- 개인화는 "JSON 자리에 사용자별 데이터를 끼우는 것"으로 환원된다.
- **수집기를 무엇으로 만들든 화면은 무풍지대.** 파이썬을 Go로 바꾸든, 서버가 실시간으로
  만들어주든, 계약만 지키면 화면 코드는 한 줄도 안 바뀐다.
  → 언어·미들웨어 교체가 이 지점부터 **공짜**가 된다.
